# 详细中文注释规范

[返回学习入口](../README.md) · [工程目录](project-structure.md) · [开发步骤](../getting-started/workflow.md)

本规范同时适用于 Cage 框架源码、标准范例，以及通过脚手架创建后由 Codex 等 agent 编写和维护的应用源码。**详细中文注释是代码交付的一部分。** 新建或修改代码时，必须让后续开发者仅凭源码及其注释理解职责、输入输出、关键步骤、设计原因、调用关系和行为边界，不能只在聊天回复或外部设计文档中解释。

注释需要回答“做什么、为什么这样做、具体怎么做、在哪些条件下成立、失败后怎样处理”。按照下面的覆盖项写到足以理解和修改代码的程度，不用每行注释、字数、行数比例衡量质量。不允许以“代码自解释”“名字已经足够清楚”免除必要的职责和接口说明；也不要把 `if`、赋值、循环等语法逐句翻译成没有信息量的中文。

## 新建与修改时的执行范围

1. 新建手写源码文件时，同步完成文件头、导出声明、类型字段以及关键流程的中文注释，再交付代码。测试、脚本、入口文件、React 组件、hooks、样式和手写 SQL 也属于源码。
2. 修改已有文件时，核对并补齐文件职责说明；为本次涉及的声明、参数、字段和流程补足注释。沿实际调用链同步更新受到影响的调用方、消费者、测试和配置说明，不能只改当前一行而留下上下游过时描述。与本次修改无关的整个仓库不要求一次性重写。
3. 调整行为、默认值、错误、权限、单位、状态或事务边界时，在同一变更中更新对应注释。移动代码时同时修正职责归属与引用，删除失效注释，不留下两个相互矛盾的解释。
4. 手写源码使用该语言支持的注释形式：TypeScript/JavaScript 的文件与接口说明优先 JSDoc，关键步骤用块注释或行注释，CSS/SQL 使用各自合法注释。JSON 等不支持注释的配置保持合法语法，在相邻文档说明字段含义并给出明确文件入口。
5. 生成契约、自动 SQL、派生测试等从声明与生成器维护注释，不能直接编辑生成结果；已执行或已发布的历史迁移不可因补注释而重写。具体边界见下文“生成物与迁移”。

## 每个文件先说明它在系统中的位置

每个新增或涉及修改的手写源码文件，开头应有中文职责说明。保留必须位于首行的 shebang 或工具指令，职责说明放在它们之后、普通实现之前。内容至少覆盖：

- **负责什么**：对应业务对象或技术能力，处理的主要问题；指出不由本文件承担但容易混淆的责任。
- **谁调用、调用谁**：所属模块、公开入口、主要上游和下游。入口文件说明如何装配注册表、服务或 Provider；纯转导出的 `index.ts` 说明对外暴露哪些职责、为什么从这里导出。
- **关键流程**：按实际顺序概述输入经过哪些处理，得到什么输出或产生什么副作用。简单纯函数文件可合并成一段；持久化、异步或多阶段流程需逐阶段解释。
- **运行与边界**：运行在浏览器、API、worker、CLI 还是测试进程，权限、事务、资源生命周期及配置由谁保证。存在 IO、缓存、共享状态或初始化行为时必须指出。

文件头写稳定的模块名和符号名，不维护易过期的代码行号或完整依赖清单。详细规则靠近实际声明，文件头负责建立读代码的路线，不能把所有实现细节堆成一份长篇设计文档。

## 导出 API、函数、类、组件和类型

对新增或修改的导出函数、类及公开成员、常量、领域声明、React 组件、hooks、接口和类型别名，紧邻声明编写中文 JSDoc。模块转导出保留原声明的详细 JSDoc，入口说明其对外职责；不要为同一接口复制多份会独立漂移的说明。

| 对象 | 必须说明的内容 |
| --- | --- |
| 函数与方法 | 解决什么问题、适用调用阶段、参数语义与约束、返回值含义、是否修改输入、是否执行 IO、失败如何返回或抛出；关键算法和取舍放在实现附近 |
| 类与公开成员 | 实例由谁创建/持有/关闭、内部状态与生命周期、依赖要求、并发访问是否支持；构造参数、方法和可读写属性分别说明 |
| 导出常量与声明对象 | 表达的业务或协议含义、使用方、取值来源、单位/默认值、改变它影响哪些行为；声明对象与实际执行不能混为一谈 |
| 接口、类型与字段 | 整体用途及数据来源，每个字段的业务语义、单位/格式、是否可空/可省略、缺省含义、只读或可写边界；联合类型逐个说明分支含义 |
| React 组件与 props | 对应页面或交互、输入数据和事件回调、状态由谁持有、可见性与权限提示、成功/失败后的页面行为；组件返回的 UI 及副作用 |
| hooks 与返回字段 | 何时读取或订阅、依赖与触发条件、状态含义、返回操作的完成条件、取消/卸载清理、缓存刷新及错误处理责任 |

函数使用真实参数名填写 `@param`，返回值使用 `@returns`，确实会抛出的错误使用 `@throws`。标签写不下的调用、权限或事务条件用正文说明。没有返回值的函数应说明副作用和完成条件，不能为了填标签编造一个结果；领域声明是配置对象，不要把 `@param` 写成不存在的顶层函数参数。泛型参数影响调用约束时说明其关系，不重复 TypeScript 已表达的类型文本。

复杂私有函数和回调同样需要说明：包括多阶段计算、SQL 构建、缓存合并、递归、重试、并发协调、状态转换及非直观数据映射。靠近相应分支解释分支成立的条件、处理顺序和保证范围。简单局部表达式可以由所在函数的说明覆盖，但不能让影响行为的隐藏规则失去解释。

## 数据与领域声明要写清业务含义

领域代码既是运行规则，也是后续 agent 理解业务的主要依据。聚合、状态、命令、事件、审批、反应、查询、任务、连接器应有各自的中文说明；框架支持的 `description` 用于简短公开说明，详细 JSDoc 用于源码维护，二者需要保持一致。普通源码注释不会自动成为权限规则、运行时校验或图谱声明，仍要填写真实 API 支持的配置。

| 声明 | 注释覆盖项 |
| --- | --- |
| 聚合与业务字段 | 对象的业务边界；字段由谁填写/计算；金额的币种和精度、数量单位、时间的时区与格式；空字符串、null、undefined、空集合分别意味着什么；敏感性、可修改阶段及关系归属 |
| 状态与不变量 | 每个状态代表的业务事实、进入和退出条件、终态允许行为；不变量保护什么规则、何时校验、拒绝后的影响，不能仅写“检查金额” |
| 命令与输入 | 调用身份和能力点、数据范围、起始/目标状态；输入来源、必填/默认/空值语义、校验与规范化；读取依赖和用途；handler 返回哪些变化；事件、事务、副作用及失败语义 |
| 事件与反应 | 事件表示哪项已发生事实、载荷字段来源、旧值/新值区别、兼容要求；消费者调用哪个命令、映射与跳过条件、执行顺序、同事务或 outbox、失败后的资源状态 |
| 审批 | 启动/取消条件、分支依据、选人来源、顺序与会签规则、结论命令、退回或转人工路径；选人不等于授予能力，AI 判断不等于硬约束已满足 |
| 查询 | 使用的安全视图/reads、调用人的 read 能力和范围、参数绑定、联表与聚合含义、排序/分页/截断、空结果含义、敏感数据及审计目的 |
| 定时任务与连接器 | 触发条件、读取/调用清单、处理上限和运行顺序；外部请求/响应映射、超时、重试分类、幂等依据、回执与补偿；fake 能验证与不能验证的范围 |

命令的状态、版本、幂等、权限、事务与审计由内核落实时，要明确这一责任分配；handler 注释不能把返回草稿描述成“已写入数据库”。`reads` 是显式只读依赖，资源 `acquires/releases` 是静态配对标签，二者都不代替真实业务动作。已有记录 `to: null` 表示保留当前状态，不能注释成“不检查状态”。

下面沿用[原语指南](primitives.md)的 Note 公开 API，展示一个完整文件的注释层次。应用仍需导出组织模型，并将本模块逐层从 domain 入口导出。示例不添加自动授权、额外持久化或不存在的框架选项。

```ts
/**
 * 部门便笺领域：声明便笺字段、状态和创建/改标题操作。
 * 模块经 domain 入口进入注册表，生成契约供业务页面调用；HTTP 将写请求交给内核。
 * 本文件只描述业务规则和字段变化，不启动服务或自行执行数据库/网络 IO。
 * 内核处理授权、范围、版本、字段校验及审计；实际可见部门由角色授权决定。
 */
import { aggregate, command, ref, scope, states, text } from '@yss123/cage-kernel';
import { z } from 'zod';

/**
 * 部门便笺：标题与归属信息作为同一个聚合维护。
 * active 表示可编辑，archived 表示归档终态；归档命令可按原语指南另行声明。
 * 本示例只开放创建和改标题，不会因声明 archived 就自动生成归档操作。
 */
export const Note = aggregate('Note', {
  description: '部门便笺',
  fields: {
    /** 便笺标题，最多 120 个字符；命令去除首尾空白后要求非空，不接受 null。 */
    title: text(120).describe('便笺标题'),
    /** 所属部门 UUID；创建输入不允许指定，内核从当前主体部门补入，用于范围判断。 */
    deptId: ref('Dept').describe('所属部门'),
    /** 创建人 UUID；内核在新建结果中填入操作者，已有记录更新时保留原值。 */
    createdBy: ref('User').describe('创建人'),
  },
  /** active 可改标题；archived 为终态，update 的 from 会拒绝对归档记录的修改。 */
  states: states('active', 'archived', {
    terminal: ['archived'],
    labels: { active: '使用中', archived: '已归档' },
  }),
  /** 声明部门范围字段和建议范围，实际授权由角色决定，并非自动授予部门可见权。 */
  scope: scope.deptSubtree('deptId'),
  invariants: {
    /** 对合并后的对象再次保证标题非空，避免其他命令将便笺写成无标题记录。 */
    titleNotBlank: (note) => note.title.trim().length > 0,
  },
});

/**
 * 创建便笺：user 身份调用 Note.create，由 new 进入 active。
 * 输入仅接收标题并去除首尾空白，归属字段交由内核按主体补入，不能由页面选择他人。
 * 没有 reads 或业务事件；handler 返回的草稿由内核继续校验和持久化。
 * 输入、权限或最终对象校验失败时不提交业务变更；声明不会给角色自动增加能力。
 */
export const createNote = command(Note, {
  name: 'create',
  description: '创建部门便笺',
  from: 'new',
  to: 'active',
  input: z.object({
    /** 用户填写的标题；trim 发生在长度校验前，最终持久化的是规范化后的文字。 */
    title: z.string().trim().min(1).max(120),
  }),
  // 新建草稿已带规范化输入和部门，返回它继续走内核流水线；这里不执行数据库写入。
  handler: (draft) => draft,
});

/**
 * 修改有效便笺的标题：user 身份调用 Note.update，只有 active 记录允许执行。
 * 内核先按调用人范围加载并锁定记录；to: null 保留已加载状态，仍检查 from 和权限。
 * 页面应传入读到的版本以检测并发修改；版本不匹配时重新加载并让用户核对内容。
 * handler 只返回标题变化，归属、状态与系统版本由内核维护；不发布业务事件。
 */
export const updateNote = command(Note, {
  name: 'update',
  description: '修改便笺标题',
  from: 'active',
  to: null,
  input: z.object({
    /** 待修改便笺的 UUID；存在不代表当前调用人有权访问。 */
    id: z.string().uuid(),
    /** 完整替换原标题，不是追加文本；不允许空标题，也不改变部门或创建人。 */
    title: z.string().trim().min(1).max(120),
  }),
  // 显式只返回标题，避免把前端传入的字段扩散为未经声明的其他业务变化。
  handler: (_draft, input) => ({ title: input.title }),
});
```

公开函数或类型的说明可以按下面的方式写。这个应用辅助函数只处理失败前缀的展示计数，不是新增 Cage API；实际业务中应明确使用它的页面或诊断模块。

```ts
/** 回放页面中已观察到的失败前缀位置；用于显示，不代表全局最小反例。 */
export interface FailurePosition {
  /** 失败动作在已观察序列中的零基索引；null 表示尚未执行到失败动作。 */
  failedIndex: number | null;
}

/**
 * 将失败位置转换为页面显示的动作序号，避免把零基索引直接交给使用者。
 * 不修改输入，也不发起回放或数据库访问；索引的合法性由创建该位置的诊断层保证。
 * @param position 诊断层提供的位置，failedIndex 为非负整数或 null。
 * @returns 一基动作序号；尚无失败位置时返回 null，让页面显示“未发生失败”。
 */
export function failureStepNumber(position: FailurePosition): number | null {
  return position.failedIndex === null ? null : position.failedIndex + 1;
}
```

## 异步、并发和恢复流程必须解释保证范围

涉及异步任务、worker、事务、重试、锁、缓存、队列、流式响应及清理时，除函数说明外，还要在关键步骤前写清以下事实：

- 任务何时被接受、何时实际执行、何时持久化、何时可视为业务完成；各阶段状态由谁更新，调用方等待的 Promise 到底表示哪个阶段结束。
- 同事务部分和事务外 IO 的边界，执行顺序的原因，失败会回滚哪些变化、哪些已发生效果无法回滚；多个步骤共同提交还是分别提交。
- 并发控制依据：版本、行锁、租约、互斥或唯一键各保护什么，保护到哪个进程/数据库范围；排序是否稳定，是否可能重复领取或乱序到达。
- 幂等键对应哪一次业务动作、由谁生成并保存、有效期和去重边界；重试是否复用原输入，结果未知时如何核对，不能把超时写成“远端未执行”。
- 失败的分类、重试条件、次数/时间预算、死信和人工恢复入口；已经持久化的回执怎样避免再次提交。不存在的恢复接口不得出现在注释中。
- 取消、断连、进程退出及卸载分别取消什么、清理什么；浏览器取消等待不保证服务端事务被取消，清理失败不能用空 catch 描述为成功。
- 缓存的数据来源、有效期、失效时机、账号/租户隔离及旧请求回填处理；权限变化时不能把仍未验证的缓存当作当前授权事实。

注释中的“原子”“恰好一次”“线程安全”“永不重复”“一定可恢复”等表述必须有实际实现支持，并写明限定范围。无法保证时直接描述当前行为、已知限制和调用方责任，不承诺超出实现的效果。

## 页面、组件、hooks 与样式

页面文件说明 URL 与参数来源、数据通过哪个生成契约或客户端获取、登录守卫与模块入口的关系。列表解释筛选/分页如何进入查询参数；详情解释如何独立按 URL 加载，不能依赖先访问列表。组件和 props 说明职责、数据归属与回调时机，hooks 说明触发、状态与清理。

在实际处理位置解释加载、空数据、网络错误、401、403、404、版本冲突和提交中状态；只描述该页面实际实现的分支，不机械列出所有错误码。明确前端 `can/useCan` 控制交互提示，真正授权由服务端完成。表单需解释草稿与已保存数据的区别、前后端校验分工、提交幂等键的生命周期以及成功后刷新哪些缓存。

effect、订阅和流式回调解释依赖为何需要、何时启动/终止、怎样阻止旧会话结果覆盖新状态。复杂布局、响应式断点、层叠与滚动、无障碍交互的样式注释说明对应使用场景与约束，不能只写“这里设置颜色”。样式文件仍需要职责说明，简单规则组可统一解释。

## 测试与维护脚本

测试文件说明被保护的业务或框架保证、使用真实数据库还是 fake、夹具的来源与隔离方式、该组测试的覆盖边界。用例名使用明确的中文行为描述；涉及边界或回归时，在用例附近解释“这个数据为什么这样准备、触发了什么风险、断言排除了什么错误”。测试 helper、共享夹具及复杂 mock 需要函数与字段说明，不能只把断言翻译成注释；fake 成功不应被写成真实第三方联调通过。

脚本文件头说明执行目录、前置配置、输入参数/环境变量的用途、读取和写入哪些路径或外部系统、是否覆盖文件、能否重复执行、失败后保留什么、如何清理。导出函数和关键阶段继续遵守本规范；不因脚本短或只供维护使用而省略副作用说明。命令示例只写变量名、示例路径和无秘密的占位值，不写真实连接串、密钥、Cookie、令牌、个人数据或初始化凭据。新增或维护脚本使用 TypeScript，不新增 `.mjs`。

## 生成物与迁移

生成文件必须由生成器写明来源、用途、重新生成入口和编辑边界；需要详细接口注释时，优先从领域 `description`、输入 schema 和真实生成规则形成，框架维护者修改生成器并验证产物。业务项目使用已安装的框架生成器；发现生成注释缺失时说明缺口，不能手改 contracts 来维持表面一致。不要声称任意 JSDoc 都会自动复制到契约，实际支持以生成器为准。

新建或尚未执行的迁移草稿应说明结构变动目的、数据兼容性、回填顺序、锁/停机影响及验证方式；无法证明影响时注明需要核对的条件。**已执行或已发布的历史迁移保持原样。** 对历史迁移的补充解释写在新文档或后续变更说明中，不为了补注释更改校验和。新增结构和数据变更使用新的迁移，仍须审查。

## 交付前逐项核对

- 新建文件是否有中文职责、调用链和运行边界；涉及的导出 API、类型字段、组件和 hooks 是否有完整 JSDoc。
- 本次改动的数据单位、空值、默认值、状态和授权条件是否解释明确；handler、框架和下游消费者的责任是否分清。
- 复杂流程是否解释关键步骤、条件、设计原因、失败与恢复；注释中的事务、幂等、并发与性能承诺是否符合实现。
- 调用方、测试、样式和脚本的相关说明是否同步更新；是否存在过时描述、机械复述或只写在聊天记录里的关键信息。
- 生成物是否通过声明/生成器更新，历史迁移是否保持不变，注释和示例是否包含秘密或真实个人数据。

代码检查和文档链接检查不能证明注释准确完整，必须结合本次 diff 阅读核对。交付说明列出注释覆盖的主要职责与边界，以及真实未覆盖项；验证仍分别报告通过、跳过和未执行。只修改注释时执行适合的格式/文档检查即可，不需要为注释新增复述实现的测试或重复全套数据库回归。

框架维护者还需注意：`cage budget` 按 TypeScript 语法 token 所占的原始物理行统计内核体积，排除普通注释、JSDoc 和纯空白；字符串、正则与跨行模板中的内容仍属于代码。同一行只计一次，不因格式化重新排版。新增详细注释不会增加实现预算；真实代码超出 5000 行仍触发 `CAGE-BUDGET-001`。应如实报告检查结果，不为通过预算删除必要说明、提高阈值或把未通过写成通过。统计逻辑的修改属于功能改动，不能混入“只补注释”的任务。
