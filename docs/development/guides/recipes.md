# 业务设计与能力选择

[返回学习入口](../README.md) · [原语示例](../reference/primitives.md) · [开发步骤](../getting-started/workflow.md)

本页负责业务规则到 Cage 能力的设计映射；工作顺序由[框架开发 Skill](../skills/cage-development/SKILL.md)统一规定，具体命令见[开发步骤](../getting-started/workflow.md)。按需要读对应配方，不要求为每个任务加载所有能力。

需要 AI 审批、业务助理、随页聊天、模型管理或性格配置时，先用 `cage capabilities` 查框架能力，再按[原生智能化指南](intelligence.md)接入。普通业务建模仍按下文声明聚合和命令；接入已有框架服务无需另建一套通用后端。

## 先确定业务边界与执行路径

开始编码前，从用户需求、业务文档和现有实现中确定以下信息。按[业务澄清与共同设计](business-collaboration.md)主动提出歧义、冲突、遗漏及有价值的建议，给出选项、影响与推荐理由，让用户选择业务规则。已明确的条件直接采用，API 和普通技术细节由 agent 查证处理；下表用于发现相关问题，不要求用户逐项填表。

| 业务问题 | 落到什么声明 | 例如 |
| --- | --- | --- |
| 管理什么对象？有哪些字段？ | aggregate、字段与 Zod 输入 | 报销单：金额、事由、部门、提单人、明细 |
| 有哪些阶段？谁能做什么？ | states、command、invokedBy | 草稿可编辑、提交后审批、完成后不可撤回 |
| 数据属于谁/哪个部门？ | 范围字段 + 角色数据范围 | 申请人看本人，经理看部门及下级 |
| 每次操作有什么硬规则？ | constraints、invariants、fail | 提单人不可审批、金额必须为正 |
| 成功后还要发生什么？ | event、reaction、approval、outbound | 启动审批、登记资源占用、推送财务系统 |
| 取消/失败要撤销什么？ | cancelOn、释放命令、补偿流程 | 取消待办、释放占用、远端撤销或人工补偿 |
| 页面需要看什么？ | 生成的 list/get、query、业务页面 | 分页、详情、按状态汇总、导出与导入 |

聚合按业务身份、生命周期和一致性要求划分。一个页面可展示多个聚合，一个聚合也可服务多个页面；不要把页面数量直接当成聚合数量。先识别必须始终成立的不变量，再确定哪些变化需要共同提交。需求没有审批或第三方时，普通命令和生成读取接口就能构成完整功能。

### 在相近能力之间作选择

| 判断依据 | 选择与边界 |
| --- | --- |
| 关系只有成员链接，还是有自己的状态与业务属性？ | 纯链接用 manyToMany；需要管理关系生命周期时建独立聚合。hasMany 是对目标 ref 的反查，变更归属走目标命令 |
| 是改变阶段，还是在当前阶段修改字段？ | 改阶段用 from/to；仅修改已有记录字段用 to: null，仍声明 from，不让 handler 直接改变 status |
| 是普通对象读取，还是汇总/联表？ | 前者使用生成 list/get；后者声明 query、reads 与安全视图。前端筛选不能承担后端数据范围 |
| 两项业务变化是否必须一起成功？ | 必须共同提交时使用同事务反应；允许稍后完成时走 outbox，明确失败、重试和结果展示 |
| 是否涉及事务外系统？ | 网络 IO 放连接器；超时可能已经远端成功，需要幂等与核对/补偿，不能用数据库事务保证远端回滚 |
| 需要人工决定，还是确定的业务联动？ | 人工/AI 审批使用现有审批流程；确定的自动联动使用事件与反应，不给每个状态变化都加审批 |

### 主体与范围必须能够落实到数据

先确定真实账号及组织关系，再列出各主体需要的能力和记录范围。当前授权模型使用已声明的归属字段；`scope.none()` 仍要求授权，但不能表达部门/创建人范围。声明了一个自定义 applicantId 或 companyName 不会自动获得“本人/本企业”过滤，应核对框架实际支持的范围字段与当前组织映射。

角色是后台分配的数据，能力是被授权的动作，门户是界面组织方式。当前会话公开类型不应通过类型断言凭空添加 roles；若需求要展示实际角色列表，应查找当前允许的读取接口或明确所需接口缺口。多角色能力/范围按框架规则合并，前端切换菜单不会自动切换服务端执行身份。用不同真实主体验证权限，不能用固定姓名或公司名称模拟范围。

## 写代码前的实现映射

理解规则并核对能力后，把“规则 → 框架机制与证据 → 修改位置 → 验收”连接起来。按当前任务写一段说明或小表即可；这里是设计示例，不是要求复制的业务或固定计划文件。

例如，用户已经明确：“已有部门通知增加归档；原有编辑者能归档；归档后保留记录、禁止修改；可见范围不变。”先查现有通知声明、编辑权限、页面及生成契约，再查[命令原语](../reference/primitives.md)。在这些证据一致的前提下，可以形成以下映射：

| 已确认规则 | 已查证的框架做法 | 受影响的位置 | 可观察的验收 |
| --- | --- | --- | --- |
| 通知可以归档并保留历史 | 在原聚合增加归档状态与命令，使用 `from/to` 表达转换；复用现有记录 | 原通知领域模块、导出、重新生成的契约与迁移草稿 | 授权主体归档后独立读取仍是同一记录，状态已改变 |
| 归档后禁止修改 | 核对所有相关修改命令的允许状态，让服务端拒绝归档状态的修改 | 原修改命令及必要的规则用例，页面按状态更新操作入口 | 直接请求修改归档记录被拒绝，刷新后内容仍未改变 |
| 原有编辑者能归档，可见范围不变 | 沿用原归属字段和读范围，明确新增归档能力由哪些现有角色获得；选人或隐藏按钮不代替授权 | 角色配置、命令能力、页面实际契约调用 | 原编辑者获得对应授权后成功；缺能力主体拒绝；范围外主体仍不能读取 |

实际任务中把“原通知领域模块”等替换为查到的具体文件、声明和签名位置；生成前说明预期契约，生成后核对实际方法。迁移是否新增、需要哪些数据处理，以真实生成差异和已有数据为准。不要从这个例子推断所有项目都需要归档，也不要顺手加入恢复、删除或通知订阅。

如果需求只说“加一个归档”，是否可恢复、谁能归档、归档后能否修改等应按对本次设计的影响提出；用户未要求恢复功能时可作为可选建议，不能擅自纳入实现。业务决定尚未取得时，映射中的相关行为保持待定，继续查证和推进独立部分。

## 新增一个普通管理对象

参考[最小便笺业务](../reference/primitives.md)在 `packages/domain/src/modules/<业务>/<对象>.ts` 声明字段、范围、不变量和本次确需的命令。便笺演示 create/update/archive；当前业务是否需要这些动作由已确认规则决定。采用唯一的导出名和必要的 `name` 覆盖，避免 index 的 `export *` 丢失重名符号。

声明时同步填写对象、字段、操作的业务名称及每个状态的 labels，按[本体建模指南](ontology-modeling.md)核对对象含义、关系和操作结果。从模块 index 到 domain 入口导出后运行 check/gen，处理缺名诊断并审查迁移，再在 `apps/web/src/modules/<业务>` 使用生成 contracts 做列表、详情、表单和操作按钮，经模块公开入口注册到 app 路由。列表和详情都有独立 URL，筛选/分页进入 query，按[浏览器配方](routing.md)检查导航，并为需要的角色授权。完整归属规则见[目录规范](../reference/project-structure.md)。不要手写后端增删改查路由、ORM 实体与 repository，也不要复制框架鉴权代码。

完成标准：已要求的动作由授权主体执行，范围外数据不可见，状态和失败行为符合已确认规则，生成契约和迁移一致。没有审批需求时不必添加审批；没有外部系统时不必添加连接器。

## 增加一对多或多对多

参考[对象关系](relations.md)，在聚合的同一个 fields 中添加 `hasMany/manyToMany`。纯关联交给框架生成中间表；关系本身有职位、状态等业务属性时再建立有意义的聚合。hasMany 反查目标上的 ref，修改归属执行子对象命令；manyToMany 用所属对象的命令返回 ID 数组。

生成后前端通过 `对象.related.字段(id, params)` 或 `use对象Related字段` 分页读取，不从普通 get 响应猜测已加载关联。给角色配置两侧 read 能力与范围；添加成员时也检查目标可见性。修改关系执行版本检查，不能把当前一页当作完整集合替换。不要创建新的业务连接池、ORM 中间实体或手写关系路由。

## 给业务单据加审批

1. 为单据补草稿、待审批、通过、驳回等真实状态及命令；提交时发事件。
2. 通过/驳回使用 process 命令，根据业务添加职责分离等约束；分支条件写在审批路由中。
3. 添加 approval 绑定和 route；只将需要的字段放进 routable，取消命令发事件并配置 cancelOn。
4. 配置实际部门负责人、角色或指定用户；给审批人配置能力和范围。
5. 页面通过待办接口操作。通过后需占用资源时用反应调用资源命令，按业务一致性选择同事务。

完成标准：提交生成待办、正确的人审批、越权和自审批拒绝、取消能结束待办、资源配对完整。转办、委派归还及当前节点前签、后签和并行必签见[审批任务流转](approvals.md)，须显式启用政策并传任务版本，旧实例是否开放签序以其快照为准。任意流程设计器、动态 JS 选人和指定节点退回仍需明确扩展范围。

## 加入 AI 审批或随页助理

先检查 domain 是否已经导出 `ai()`，再按需求修改已有声明或启用一次。AI 审批配置在业务模块的现有 `step` 内，填写 `kind: 'ai'`、审核策略、取证字段/查询与 `handoff`，由 `approval` 绑定自动执行角色和结论命令。业务助理使用框架生成的工具，前端通过 `useAssistant` 与 `useAiPageContext` 接入当前页面；悬浮窗、Markdown 和确认交互由应用实现。

模型地址、协议和密钥通过 `managedModel` 对应的 Admin 配置管理，性格也使用框架现有管理页。先完成系统迁移和必要授权，按[智能化指南](intelligence.md)的接入顺序、SDK 示例和验收步骤验证。分别说明框架支持、应用已启用和真实联调结果；空白模板中的参考代码不参与运行。

## 增加报表或复杂列表

普通分页和详情先使用生成的 list/get；汇总、联表等需求再添加 query。写清 reads、输入 schema，选择参数化 SQL 或 build；只查对应 safe 视图，不为“报表方便”切到管理员连接。

重新生成后使用 `queries.你的查询()` 或生成 hook。检查真实调用人的 read 能力和数据范围；管理员能看到结果不能证明普通用户的报表正确。

## 接入外部系统

沿 `packages/domain/src/integrations/erp.ts` 的结构声明 host、密钥名、操作 schema、outbound 和 inbound。远端成功后的字段回写也走 external 命令。先用 fake 完成本地链路，再在测试环境做真实联调。

明确重复请求如何识别、哪些错误重试、回执晚到怎么办、取消后如何补偿。不要假设本地事务可以回滚已经提交给第三方的写入。

## 增加导入或导出

在客户实际需要的业务页调用客户端/生成契约，展示任务进行中、完成和失败。导入映射到用户可调用的命令，准备与该命令输入匹配的 CSV；不要生成直接写业务表的上传接口。

明确逐行还是整批原子模式、失败报告如何呈现、任务过期如何处理。任务提交成功不能立即标成导入/导出完成，worker 与下载时授权也是链路的一部分。完整方法、CSV 例子与协议见[业务页导入导出](transfers.md)。

## 由采购演示换成客户业务

空白模板不需要清理采购业务，直接从 `packages/domain/src` 新增自己的声明和页面；参考源码在 `docs/examples/purchase-admin`，不在运行入口中。下面的替换步骤只适用于采购模板。

建议先保留运行薄壳和一条可验证的演示链路，新增真实业务并接通页面，再移除不需要的演示引用。清理时沿领域导出、反应、审批、连接器、查询、任务、页面和 graph.labels 一起检查，避免残留仍在运行的自动任务。

组织模型仍从 `@yss123/cage-admin/domain` 导出。已执行迁移作为历史保留，新表/删表通过新迁移表达；需要保存旧数据时先制定迁移方案，不能只把整个 migrations 文件夹删除。

```text
阅读当前项目 AGENTS.md，按 docs/development/skills/cage-development/SKILL.md 完成理解、澄清、能力查证、实现映射、编码和验收。
业务：……；角色与数据范围：……；状态与允许动作：……；审批/外部系统/资源占用：……。
先用业务语言说明对本次目标的理解，主动指出疑点，给出可行选项、影响与推荐，让我选择；已明确条件不重复询问，普通技术细节自行查证处理。
查现有实现和当前版本 API，写代码前简述已确定规则如何落到 Cage、改哪些模块、如何验收；能明确实现的部分直接推进，等待业务决定时继续独立工作。
遵守项目目录与中文注释规范，生成文件通过 cage gen 更新，按改动完成必要验证。
交付时说明用户如何体验、管理员需配置什么，以及通过/跳过/未执行的检查。
```
