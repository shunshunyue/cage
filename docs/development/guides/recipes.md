# 把业务规则变成 Cage 声明

本页帮助你选择机制。目标是得到一个清楚的对应关系：**业务规则 → 框架声明 → 代码位置 → 可观察结果**。规则有歧义时先按[业务协作](business-collaboration.md)处理。

## 先识别对象、动作与一致性

对象有自己的身份、生命周期和必须成立的条件时，通常形成一个聚合。页面数量不决定聚合数量；一个页面可以读多个对象，一个对象也可以出现在多页。

动作写成命令，成功后的事实写成事件。确定两项变化是否必须共同成功，再选择同事务反应或异步执行。第三方已经发生的变化无法由本地事务撤回，需要明确外部幂等和补偿。

| 业务问题 | 使用机制 | 用法 |

## 写代码前说明对应关系

假设已确定：“已有部门通知增加归档；原编辑者可归档；记录保留，归档后不可修改；可见范围不变。”

实现说明可以是：

| 规则 | 框架与修改 | 验收 |
| --- | --- | --- |
| 保留归档记录 | 在现有聚合增加归档状态和标签 | 归档后安全读取仍返回同一 id |
| 原编辑者执行 | 新归档命令并配置相应角色授权 | 有权者成功，缺能力者拒绝 |
| 归档后不能编辑 | 现有编辑命令 from 排除归档状态 | 直接发修改请求也被拒绝 |
| 范围不变 | 复用归属和已有范围 | 范围外账号仍不可读 |

实际工作用查到的模块、符号、签名和生成差异替换抽象位置。是否新增迁移由结构变化决定；是否能恢复、谁能恢复，属于另一个需要业务依据的动作。

小改动用一两句话完成说明即可。新建业务还要讲清对象含义、关系方向和基数、状态以及动作后的结果。

## 复用已有实现

先搜索当前应用，再查安装包的公开能力。已有 AI、审批、文件和组织运行时应从现有入口扩展，避免在应用中复制框架实现。

空白模板的真实 domain 只有组织基础，直接新增自己的模块。采购模板的替换需要沿领域导出、反应、流程、集成、任务、页面与显示名称一起处理。已执行迁移作为历史保留，用新迁移改变结构。

目录归属见[工程组织](../reference/project-structure.md)。设计明确后按[开发步骤](../getting-started/workflow.md)实施，按[验证参考](../reference/verification.md)回到业务例子验收。
