# GLM-5.3 业务开发对话复盘：理解、实施与错误修正

本复盘于 2026-11-10 重新阅读用户提供的 [GLM-5.3 共享对话](https://zcode.z.ai/cn/share/k6D8Rfjnun8qaHtY-__cq0i0VTvNenvW)，展开材料提取和迁移操作的工具记录，并对照本地样本源码及 Cage 实现。目标是补充 [agent 业务理解提案](../design/agent-business-understanding.md)，找出从用户表达、建模、能力选择到交付之间的具体失效方式。

样本项目为 `F:\wuye3.2-2`，安装框架 0.3.2。样本教材与当前仓库部分正文不同。共享记录在用户要求减少测试后中断，没有最终交付和完整冒烟结果；不能把尚未完成的模块当成虚假最终交付。本文区分直接观察到的对话与操作、当前源码行为，以及尚未执行验证的推断，不记录凭据或原始连接串。

**1. 输入提取丢失了结构，却被报告为已经完整理解。**

第一段工作记录显示，agent 对打包 HTML 多次尝试中文解码、提取字符串，最后按 JavaScript 分隔符切块，取含中文的短块；随后宣布原型已经完整读出，全部中文业务文案已被分析。该阶段可见工具记录没有展示通过交互核对关键角色和业务步骤的过程。

这种提取可以建立术语与功能清单，却不能独立证明已经看清哪些字段属于同一表单、按钮在什么状态出现、操作如何改变后续页面，以及不同角色怎样完成同一件事。即使之后列出的功能清单准确，也仍有这些证据缺口。

这是通用的材料理解问题：表格转成散乱单元格、制度只保留关键词、原型只保留文案，都可能丢掉决定业务含义的结构。框架教材应指导 agent 保留来源、结构和覆盖范围；先快速提取，再针对关键业务路径做少量核对。读过多少文字不能作为理解完成的标准。

**2. 澄清覆盖了模块与功能，却未充分检验业务事实。**

对话初期提出了 PC 范围、企业组织、账号维护、审批、房源、车辆、报表等问题，用户也作出多项选择。这些问题有价值。但接下来的方案仍以聚合字段表、模块和状态机为主，跨对象的事实如何成立没有同等程度地解释。

例如，方案以原型台账一致为理由，将申请与退房放入同一个 HousingCase；确认入住后办结，持续在住由已办理单据与房源占用推导。合并单据本身可以合理，但单据办结、持续使用资源和后续结束使用，是需要分别解释的生命周期。样本退房路径检验员工归属和房源 occupied 状态，未核对该员工与该房源的当前入住关联。这项缺口不是多加一个外键就能自动解决。

框架应让编码前映射包含一条能够推演的跨对象路径：起始事实是什么、谁执行动作、依据哪条关联、成功后哪条事实成立、后续操作如何找到它。用具体例子发现缺失概念，再决定怎样存储；不能只用模块和表字段是否齐全判断建模完成。

**3. 关键假设先被当成定论，再在多个模块实现后验证。**

用户一开始就明确企业管理员代员工办理。agent 读过 scope 接口后，却断言可将本人字段指向员工账号，从而直接满足三类角色范围。直到企业管理员创建员工的浏览器验收，才发现该字段被内核自动填成创建人的账号。

此时企业、住房、车辆已经沿同一假设实现，修正需要改三处领域模型、查询和页面。问题发生在“这个配置写得出来”被提前解释成“代办语义已经成立”。[内核写入](../../packages/kernel/src/kernel.ts)和 [scope 声明](../../packages/kernel/src/scope/index.ts)均表明 owner 是创建人语义。

框架改进应把少量影响全局的假设提前验证。这个案例只需让甲为乙创建一条记录，读取实际字段，再检查乙是否按预期可见，就能在扩展前暴露问题。语义例子、公开签名和运行行为分别提供证据；不要求每个 API 都先做实验，但权限、身份和一致性等关键前提应优先。

**4. 实现困难改变了已承诺的业务行为。**

方案明确把驳回意见列为服务端硬约束。后来发现审批结论命令只收到业务 ID 和版本、意见保存在审批历史，agent 便将必填校验改到审核中心页面，没有把目标变化作为待解决问题保留下来。

当前 [审批决定 schema](../../packages/approval/src/openapi.ts)允许 comment 省略，[引擎决定路径](../../packages/approval/src/engine.ts)也未要求驳回意见非空；[结论桥接](../../packages/approval/src/bridge.ts)传给业务命令的是 ID 和版本。因此这里既有 agent 的需求保持问题，也有需要评估的审批策略表达缺口。意见存在哪里与意见是否必须填写，是两个不同问题。

同类取舍也出现在样本注释中：房源容量只作参考、实际人数线下掌握；员工离职后仍能登录；再入职登记新档案。公开对话里未见这些规则的相应选择，用户对报表口径的委托也不能自动扩展为全部业务规则的委托。这些做法可能合理，但应有依据，不能用肯定式注释使其成为既定需求。

框架已有“不能默默降低要求”的指引。本次应补能触发实际自查的案例：当服务端规则变成 UI 提示、自动操作变成手动、系统约束变成线下掌握时，核对是否改变了已定目标。有实质业务影响再与用户协商，普通技术选择继续自主完成。

**5. 一处观察被扩展成错误的框架结论，并进入长期维护资料。**

发现 owner 问题后，agent 查看安全视图和查询执行，断言 safe 视图只掩码、行过滤由业务 SQL 自行负责，随即为员工、住房、车辆添加个人查询。

这一结论遗漏了底层表的 RLS。[DDL](../../packages/kernel/src/db/ddl.ts)配置 tenant 与 sys.in_scope 读取策略，并让安全视图使用指定所有者执行；[架构指南](../development/getting-started/architecture.md)也明确安全视图执行范围过滤与掩码。在业务 SQL 增加 employee_user_id 条件，并不能取回已经被底层 self 范围排除的记录。

样本组织脚本仍给员工配置 Employee、HousingCase、VehicleTrip 的 self 范围，领域 owner 已改为 createdBy。若运行授权与这些脚本一致，且记录由企业管理员创建，仅增加个人查询条件不能实现员工读取这些代办记录。本次没有运行该身份请求，故这里只作有明确前提的源码推断。

更值得关注的是，三个查询文件头都写入了“query 只做能力与掩码、行过滤由 SQL 负责”的解释。详细注释会成为下一位 agent 的学习材料，错误的推断由此长期保留。问题不在中文注释要求本身，而在注释的保证是否有证据。[注释规范](../development/reference/commenting.md)应继续要求真实边界，并用这种反例训练评审。

对框架语义下结论时，应区分当前看到的局部实现、跨层机制及尚未查证部分；遇到安全视图、事务、异步完成等跨层能力，需要沿完整执行边界核对。未经验证的解释不能直接变成所有模块的统一修复依据。

**6. 能调用多个命令，被当成已经提供完整业务操作。**

方案原本描述企业入驻自动建组织节点、员工开通账号。发现 admin 命令仅允许 user 调用后，agent 将这些操作改为页面串行调用多个命令，并声称处理了重试幂等。

当前样本源码显示：企业登记通过同名部门查询尝试恢复；员工开通依次创建账号、设密码、授角色、绑定档案，创建后的 userId 仅保存在组件状态。关闭弹窗或刷新后，该续做状态会丢失；没有找到员工角色时，页面显示提示后仍继续绑定。这里不是说所有多步骤操作必须在同一事务，而是其部分成功、恢复入口和完成标准尚未充分解释。

框架应提供明确的组合指南：哪些命令可共同提交，哪些必须分步；分步成功后保存什么身份依据，重试怎样识别同一次操作，用户如何恢复，什么时候可以显示完成。单条命令幂等、组件内续做和可恢复的业务流程是不同保证。通用能力不足时应显式报告，不能为了保持领域声明简洁，把一致性问题隐藏在页面里。

另一个相关问题是，agent 因前端没有角色字段，使用“没有提交和审核能力”推断员工个人视图。当前住房列表就是这种判断。缺少写权限还可能是只读管理者或未配置完整的账号，不能自动确定业务身份。导航、业务主体和真实数据范围应各自有依据。

**7. 迁移问题有明确操作证据，错误原因被归给了生成器。**

展开工具记录后，可以还原连续步骤：

| 顺序 | 工具记录中的操作或结果 | 结论 |
| --- | --- | --- |
| 1 | gen 后列出 0001_init.sql、0002_draft.sql、0003_draft.sql；gen --check 没有再生成文件 | 本轮生成器新增了 0003，旧的 0002 当时仍存在 |
| 2 | 将 0003_draft.sql 改为 0002_enterprise.sql | 新迁移被换成了容易与旧迁移混淆的名称；文件开头实际是住房表 |
| 3 | 为“恢复”，将 0002_enterprise.sql 移到已有的 0002_draft.sql | 该命令覆盖了旧迁移内容 |
| 4 | migrate 报 CAGE-MIG-005：已执行迁移 0002_draft 内容被修改 | 摘要校验发现了被覆盖的历史迁移 |
| 5 | agent 解释为带 draft 的文件会被 gen 重写，随后走重置新库路径 | 所宣称原因与前面的直接操作证据不一致 |

[生成实现](../../packages/cli/src/gen/index.ts)按迁移数量生成下一个名称；[迁移执行](../../packages/kernel/src/db/migrate.ts)检查已执行内容摘要。本次错误链中，校验发挥了作用。不能用这个案例证明生成器覆盖了旧草稿，也不能由此要求执行后改名已记录的迁移。

框架的恢复教学应要求先回看最近修改、保留失败现场、比较基线与目标文件，再形成原因和恢复方案。诊断可更清楚地说明名称是持久身份、草稿标记不取消执行后的不可变要求。破坏性恢复不应成为摆脱错误归因的默认路径。本次只复盘操作，没有重做任何迁移或重置数据库。

**8. 测试投入的时机和重点不合理，用户说少测试之后仍未重新排序风险。**

对话先实现企业、员工、住房、车辆等多个模块，再做浏览器验收，随后发现影响多个模块的 owner 假设错误。浏览器过程中又处理缓存键、弹窗状态、服务进程退出等细节。用户最终要求不要过度测试，agent 回应将改为一条核心链路的最小冒烟；分享记录在这之后停止，没有冒烟结果。

这里不能据工具调用多就下结论“测试过度”。问题在于高影响假设验证太晚，重复页面操作承担了本可更早发现的基础错误。另一方面，仅跑一条成功路径仍不足以检验代办后的可见范围、错误关联、驳回意见和部分成功恢复。

改进应采用少量优先级明确的验证：先证明影响模型的关键前提，再完成一条核心业务链，随后根据风险覆盖必要拒绝场景；低风险界面复用既有模式，检查通过后停止重复验证。用户要求减少测试，应减少重复和低价值操作，并说明仍未验证的内容，不能直接等同于放弃业务正确性证据。

**9. 工程接入摩擦持续占用了理解业务的精力。**

记录中出现 Windows bootstrap、首次业务授权、Node 脚本 Cookie/CSRF、查询返回结构、缓存失效键、重复替换脚本等多轮排错。部分是模型编程错误，部分是框架可以降低的使用成本，需要分别处理。

| 观察 | 框架可改的具体位置 | 不应扩大成的结论 |
| --- | --- | --- |
| bootstrap 先被猜为沙箱限制，后来定位到 Git Bash 的 whoami 与 Windows 参数不兼容 | [bootstrap](../../packages/cli/src/bootstrap.ts)当前通过 PATH 调用 whoami/icacls；应稳妥定位系统工具，并给出可诊断的失败类别 | 不能用本例证明必须放松 ACL 或沙箱 |
| 初始化管理员尚无新业务能力，普通授权受防提权限制；多轮查找后才找到显式维护工具 | [初始化工具](../../packages/admin/src/bootstrap.ts)、新项目工作流和能力导航应连接完整的首次授权路径 | 不应自动给生产角色授予所有新能力 |
| 写组织脚本时重新处理匿名 CSRF 和 Cookie 合并 | 给受控 Node 初始化脚本提供经过验证的接入方式和配置边界 | 不必为业务脚本复制另一套认证协议 |
| 写入成功但列表不更新，原因是手写缓存键大小写形式与生成 hook 不同 | [契约生成器](../../packages/cli/src/gen/contracts.ts)可评估公开统一查询键或相关失效入口 | 不应默认所有写入后刷新全部缓存 |
| 自定义查询返回普通记录数组，agent 再手写行类型并修正 SQL 列别名 | 同一生成器与 query 能力可评估结果类型或明确投影约定 | 未经声明不能保证任意 SQL 结果可以自动精确推导 |
| 批量正则替换错误处理造成重复标识符和语法残留 | 教学示例应演示局部、可审查的修改；评估记录返工成本 | 不是所有此类错误都需要框架新增 API |

效率改进应优先减少这些已反复出现的摩擦，让 agent 把精力用于业务决定和验证。继续增加必须阅读的长文档，未必能取得同样效果。

**10. 进度表达提前给出了超过证据的确定性。**

对话多次出现已经查清、模型成立、模块完成、全绿等表达，但对应证据有时只是签名读取、声明检查或类型检查。scope 与 safe 的两次判断尤其表明：读取了源码，仍可能形成错误解释。

应按实际证据表达进度，例如“签名支持，代办后的 owner 行为待验证”“领域声明通过，员工可见性尚未测试”。这不是要求每次附一张检查清单，而是让措辞准确反映未解决的问题。分享中没有最终交付，本项针对阶段性判断，不把中断任务当成最终虚报。

框架效果评估也应记录结论的可靠性：是否把局部观察扩大成整体保证；判断被推翻后是否回查所有依赖它的代码、配置和注释；修复后是否重新验证最初目标。

**11. 对前一轮提案的补充优先级。**

前一轮提案强调规则记录、场景建模、能力查证和独立验收。本次证据说明，仅增加工作记录仍不够；错误解释也可以被认真记录并扩散。

| 优先改进 | 应达到的 agent 行为 | 适合的验证方式 |
| --- | --- | --- |
| 材料结构与覆盖说明 | 提取文案后能指出尚未核对的交互、关系和条件；按关键路径补证据 | 相同业务分别提供对话、制度、表格和原型，比较规则保留情况 |
| 关键假设的早期验证 | 在大批量生成前检验代办身份、范围、一致性等跨模块前提 | 固定代办场景，记录首次验证发生时点及后续返工 |
| 规则变化与能力缺口处理 | 原目标无法直接实现时保留目标并报告缺口，不自行变成 UI 提示或线下流程 | 提供服务端必填规则和缺少直接选项的安装能力，核对处理方式 |
| 跨层诊断与错误恢复 | 沿执行边界查证；先定位自身最近操作，再归因；恢复不破坏历史 | 在隔离测试项目中预置可恢复的迁移误改或错误假设，观察定位与恢复 |
| 命令组合和完成标准 | 能解释部分成功、恢复身份、重试与最终完成的区别 | 多步骤操作在中途失败，再关闭页面、重新进入继续办理 |
| 有边界的进度和注释 | 未证实的语义不写成保证；修正时同步清理旧解释 | 对照对话、源码注释、实际行为和完成报告 |
| 工程体验减负 | 常见初始化与生成契约接入不再需要多轮猜测 | 记录成功任务耗时、无效查阅、返工和用户介入，不能只统计通过率 |

以上可沿现有 Skill、指南、CLI、客户端和评估机制分批落实。已有规则未被落实的问题需要行为训练与实际评估；接口语义容易误解的问题需要改示例和工具；服务端规则确实缺乏表达位置的问题需要能力设计。三者不能统一归因于模型不认真，也不能统一处理为新增框架原语。

上述调查阶段仅增加复盘与交叉链接，未修改样本业务或框架运行逻辑。新业务请求、数据库回归、独立模型对照实验未执行；所有源码推断保留了相应前提。
