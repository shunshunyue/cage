# 采购 OA 逐项浏览器验收

本说明用于框架仓库中的真实采购示例。应用能力及权限配置见 [采购范例导读](ai/purchase-example.md)，流程与任务语义见 [审批指南](ai/approvals.md)。下面的隔离演示只帮助准备可重复的场景，启动成功和自动回归通过都不代表浏览器验收已完成。

## 启动独立演示

在仓库根目录安装依赖并构建框架；领域变化后先生成并审查契约和新增迁移。脚本不读取或修改采购示例的数据库 `.env`，使用 testkit 新建本次独立 PostgreSQL 及业务数据库，应用迁移只作用于这个临时库。

```powershell
pnpm install
pnpm build
pnpm --filter @app/purchase-admin gen
# 审查生成差异后启动；脚本会再次构建示例应用并复制 Web 静态快照。
node scripts/start-purchase-oa-demo.ts
```

默认地址为 `http://127.0.0.1:3000`；端口已占用时，在启动前设置 `$env:CAGE_DEMO_PORT = '3001'`。脚本使用真实 domain、组织命令、审批引擎、HTTP 服务和 worker，不提供替代审批路由或模拟 API。

启动后终端只打印普通运行信息，输出目录为 `.cage/purchase-oa-demo-<时间戳>`：

- `info.json`：地址、账号用途、各场景单据路径、停止标记路径及能力边界，不含密码或数据库连接串。
- `credentials.json`：随机账号密码和本次 AI 加密密钥；创建时已限制本机文件权限，不应提交或复制到验收报告。
- `web/`：本次构建的静态页面快照，后续开发重建不会覆盖运行中的资源。

结束后按 `Ctrl+C`，或在 `info.json` 的 `stopFile` 路径创建一个文件。脚本依次停止 worker、API，删除本次测试数据库并关闭自建 PostgreSQL；普通运行信息和受限凭据文件保留在输出目录，数据库被清理后这些账号不再有效。

## 本次准备的人员与边界

| 账号 | 用途 | 批准额度 |
| --- | --- | --- |
| `oa.buyer` | 采购申请、材料/名单编辑、提交、取消 | 无批准能力 |
| `oa.manager` | 部门负责人，处理 AI 人工接管及经理节点 | 100,000 元 |
| `oa.backup` | 转办或加签的备选审批人 | 100,000 元 |
| `oa.technical` | 技术复核 | 100,000 元 |
| `oa.quality` | 质量复核 | 100,000 元 |
| `oa.finance.a` / `oa.finance.b` | `finance` 共享候选池成员 | 每人 100,000 元 |
| `oa.no-access` | 无业务权限反例 | 无批准能力 |
| `oa.low-ceiling` | 额度不足反例 | 1,000 元 |

审批人均以真实用户登记 active 协作名录；申请人与需要选人的审批人拥有 `ApprovalMember.read` 及 `ApprovalMember: all` 范围。用户没有因为名录而获得 `User.read`。财务候选身份通过额外的 `finance` 角色分配，常规审批能力来自各人的角色。

未配置 `main` 模型，也没有固定返回结果的测试模型。每张单据提交后，真实 AI 节点因缺少模型按 `onFailure: 'manual'` 转部门经理接管；经理在“AI 材料预审”通过之后才进入“部门经理审批”。此环境能验证故障转人工和后续 OA，不能证明真实模型的 pass/return/manual 判断质量。需要模型联调时按智能能力指南另行配置并验收。

ERP 出站采用框架 fake 连接器，正常批准后会回写 `OA-DEMO-` 单号；不连接真实外部 ERP。库存 `A-01` 预置 100 件，每张单据申请 2 件，演示验证库存锁生命周期，不证明多订单累计扣减或仓库核算。

## 按场景操作

13 张预置单据均为草稿，用途以中文场景名开头，`info.json.cases` 保存对应详情 URL。先用申请人提交，再切换到各任务处理账号；每次动作后同时检查待办、等待任务、详情审核记录和业务状态。

| 场景 | 操作 | 应观察的结果 |
| --- | --- | --- |
| 普通经理审批 | 完成人工接管，再通过经理节点 | 最终 approved，库存锁建立，稍后回写 ERP 单号 |
| 50,000 元边界 | 经理通过 | 不产生财务候选待办 |
| 60,000 元财务候选 | 财务甲领取、释放，财务乙刷新后领取并通过 | 两人最初看到同一任务；未领取不能决定；最后才批准 |
| 技术质量双人会签 | 经理后，技术、质量分别通过 | 第一人通过仍待审批，第二人完成后才批准 |
| 部门经理转办 | 经理转给备选审批人 | 原人失去待办，接手人决定，历史保留转办原因 |
| 委派归还 | 经理委派技术，技术完成归还，经理通过 | 技术不能直接作最终结论，归还后仍由经理确认 |
| 前置加签 | 经理为技术添加前置签署 | 经理先等待，技术完成后经理恢复可处理 |
| 后置加签 | 经理为质量添加后置签署 | 质量先等待，经理完成后质量可处理 |
| 并行加签 | 经理添加技术并行签署 | 两者都完成之前单据不批准 |
| 退回修改再提交 | 经理退回，申请人补用途并重新提交 | 草稿可修改；新轮次重走 AI 和人工，旧理由保留 |
| 等待加签时取消 | 经理添加后置签署，申请人取消 | 当前/等待任务全部关闭，晚到决定不能恢复流程 |
| 低额度结论拒绝 | 1,200 元单据转给低额度审批人并尝试通过 | 额度约束拒绝，单据仍待审批，不产生库存锁 |
| 专业会签后财务受理 | 60,000 元单据依次通过经理、两位专家、财务 | 阶段顺序正确，最后才批准 |

另以 `oa.no-access` 访问采购列表、详情深链接与审批入口，核对服务端权限拒绝；以普通账号检查刷新、前进后退、登录回跳及未知路径。动作冲突时刷新任务并重新判断，不自动重发旧 `revision` 的审批决定。每项验收应分别记录“通过 / 失败 / 未执行”、实际操作者和观察结果，不能仅因为脚本造数成功填为通过。
