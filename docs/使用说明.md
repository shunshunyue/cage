# Cage 框架使用说明

适用版本：当前 `0.2.0` 源码及尚未发布的反馈改进；更新日期：2026-11-03。已发布状态见[发布记录](release-0.2.0.md)，本轮源码改进见[实施记录](feedback-refactor.md)。命令以 Windows PowerShell、框架目录 `F:/cage` 为例。

**当前可以使用框架开发业务、连接真实 PostgreSQL、运行采购示例，以及在 Web 图谱中查看声明关系；设计文档尚未全部交付。** 完成情况和差异见 [设计实现对照表](design-coverage.md)，以前实际执行的验证结果见 [实施与验收记录](implementation-status.md)。本文整理使用方法，没有重新运行整套测试。

## 1. 现在怎么打开

这台机器的采购示例已配置数据库。先确保 `.env` 指向的数据库服务正在运行，然后启动应用；已有数据库和表会继续复用。

在第一个 PowerShell 终端执行：

```powershell
cd F:/cage
pnpm --filter @app/purchase-admin dev
```

在第二个终端打开图谱服务：

```powershell
cd F:/cage/examples/purchase-admin
pnpm exec cage graph
```

如果图谱服务已经运行，直接访问原来的地址即可，不必再启动一次。

| 要看什么 | 当前本机地址 | 说明 |
| --- | --- | --- |
| 采购工作台 | <http://localhost:15173> | 采购单、库存台账、审批待办 |
| 系统管理 | <http://localhost:3000/admin/> | 用户、部门、角色、审计、异步任务、同步记录 |
| 本体图谱 | <http://127.0.0.1:15418> | 对象字段、业务关系、规则问题 |
| API 健康检查 | <http://localhost:3000/healthz> | 用于检查 API 是否已启动 |
| OpenAPI JSON | <http://localhost:3000/api/openapi.json> | 自动生成的接口说明 |

工作台默认端口是 `5173`；本机因 Windows 保留端口已改为 `15173`。以终端打印的地址为准。`.env` 中的 `CAGE_WEB_PORT` 控制 Web 端口，`PORT` 控制 API 端口，修改后重启 `dev`。

新组织在执行迁移后显式运行 `pnpm exec cage bootstrap --credentials-file .cage/admin-credentials.json`，管理员凭据只进入新的受限文件，日常 API 启动不初始化组织或输出密码。已有组织不会重置凭据；网页登录账号和数据库账号是两回事。

按 `Ctrl+C` 结束 `dev` 会关闭 API、worker 和 Web。数据库服务由使用者自己的数据库工具或部署平台管理。

## 2. 框架、范例与模板分别做什么

| 目录 | 用途 | 什么时候修改 |
| --- | --- | --- |
| `F:/cage/packages` | 框架实现：内核、HTTP、权限、审批、连接器、CLI 等 | 扩展或修复框架能力 |
| `F:/cage/examples/purchase-admin` | 可直接运行的标准范例，展示采购与库存锁流程 | 学习框架、运行演示、维护标准范例 |
| `F:/cage/templates/app` | 采购示例分发模板 | 从标准范例同步采购业务 |
| `F:/cage/templates/blank` | 空白业务分发模板 | 维护空白工作台及最小组织领域 |

**最终创建的新项目来自用户选择的模板。** 交互终端通过方向键选择空白或采购示例，也可使用 `--template blank` 或 `--template purchase`；非交互脚本必须明确指定。CLI 使用包内模板，不复制框架实现、`.env` 密码、运行数据或 `node_modules`。空白模板只注册组织模型，采购范例在 `docs/examples/purchase-admin` 中作为离线参考，不参与建表或运行。

导入导出属于可供各业务选择使用的框架接口，页面由业务前端决定。`0.2.0` 的 HTTP、SDK 和任务状态接入见 [导入导出说明](导入导出.md)。

维护者修改范例后，需要把可分发内容同步并重建 CLI，下一次创建才会使用更新后的模板：

```powershell
cd F:/cage
pnpm template:sync
pnpm --filter @yss123/cage-cli build
```

普通业务项目使用者无需执行模板同步。

## 3. 新机器第一次安装

使用 Node.js 24、pnpm 10，并准备一个已经存在、可连接的 PostgreSQL 数据库。首次只提供一次管理员连接，由框架自动准备账号和本地凭证。

```powershell
cd F:/cage
pnpm install
pnpm build
cd examples/purchase-admin
# 首次配置时复制，已有 .env 时保留并直接编辑。
Copy-Item .env.example .env
# 编辑 .env，只填写 CAGE_ADMIN_DATABASE_URL，例如：
# postgresql://postgres:管理员密码@127.0.0.1:5432/已有数据库名
pnpm exec cage init
pnpm gen
# 审查 db/migrations 后执行：
pnpm migrate
pnpm exec cage bootstrap --credentials-file .cage/admin-credentials.json
pnpm dev
```

1. `init` 使用管理员连接创建 Cage 账号、schema 和授权，生成独立随机密码及 Cookie 密钥，自动填写 `.env`。它连接已有数据库，不创建数据库或业务表。
2. 成功后管理员连接会从 `.env` 移除，现有业务配置保留。重复执行会验证已有账号，保持密码一致；失败时回滚数据库并保留原配置。
3. `gen` 生成契约、SQL 和迁移草稿，审查后执行 `migrate` 更新表结构。
4. `bootstrap` 显式初始化组织并通过新受限文件交付凭据，不自动授予业务能力。`dev` 连接配置的数据库并启动 API、worker、Web；domain 修改后只重新生成文件，表结构迁移仍须手动执行。

PostgreSQL 管理员通常叫 `postgres`，实际账号叫 `root` 时使用该名字。连接密码的特殊字符需要 URL 编码。角色属于整个集群，若已有 Cage 账号但本项目没有保存连接，命令会提示复用原凭证，不会重置其他项目的密码。

## 4. 数据库由谁连接，在哪里看数据

| 层 | 职责 |
| --- | --- |
| `@yss123/cage-kernel` | 连接池、事务、写入流水线、安全视图、数据范围与数据库权限 |
| `@yss123/cage-cli` | `init` 自动准备账号及 `.env`，生成契约与迁移草稿、手动执行表结构迁移 |
| 业务项目 | 配置连接地址、声明业务模型、保留 API/worker 薄启动入口 |

**项目不需要再写 `pg.connect()` 或连接池。** 现有 API 入口 `apps/api/src/main.ts` 调用 `createServer({ domain, ... })`，框架从环境中取得连接；worker 同样由框架装配。

当前开发库可用 DBeaver、DataGrip 或 pgAdmin 连接：

| 项目 | 当前值 |
| --- | --- |
| 主机 | `127.0.0.1` |
| 端口 | `54329` |
| 数据库 | `cage_dev` |
| 用户及密码 | 从项目 `.env` 中选择对应角色的连接串 |
| 测试集群 | `127.0.0.1:54330/postgres`，与开发集群隔离 |

| 环境变量 | 用途 |
| --- | --- |
| `CAGE_ADMIN_DATABASE_URL` | 首次 `cage init` 使用的已有数据库管理员连接；成功后从文件移除 |
| `CAGE_APP_DATABASE_URL` | init 自动填写；API/worker 的业务连接，角色 `cage_app` |
| `CAGE_READ_DATABASE_URL` | 读侧连接，角色 `cage_read` |
| `CAGE_MIGRATE_DATABASE_URL` | 迁移连接，角色 `cage_migrate` |
| `CAGE_TEST_DATABASE_URL` | 独立、可丢弃测试集群的管理连接 |
| `CAGE_COOKIE_SECRET` | Web 会话签名密钥 |
| `CAGE_STAGE` | 连接器阶段；本地为 `fake`，另外支持 `test`、`prod` |

**配置位置：业务项目根目录 `.env`，与 `package.json` 同级。** 首次复制 `.env.example`，只填 `CAGE_ADMIN_DATABASE_URL` 后运行 `pnpm exec cage init`；三个业务连接和 Cookie 密钥会自动生成。已有三种账号连接可直接复用，无需管理员密码。三个数据库连接指向同一个数据库，仅账号权限不同。CLI 自动读取该文件，终端或部署系统已经设置的环境变量优先。修改后重启 `dev`；`migrate` 在下次执行时读取。改后仍连接旧地址时检查外部同名变量。

业务表主要在 `core`，组织、审计、outbox 等在 `sys`，代码内审批表在 `flow`。具体表名可看图谱卡片底部或 `generated/sql/schema.sql`。连接已有数据库不等于自动识别或接管其中任意旧表；历史业务表需另行映射并审查迁移。

读账号只允许通过安全视图按会话上下文查询，数据库工具直接登录后“查不到基表”不代表数据丢失。业务增删改仍通过命令执行。

测试工具会初始化集群级角色，因此测试连接不能复用开发库或生产库。需要另开业务项目时，也建议使用独立集群与端口：框架的三个角色名属于整个 PostgreSQL 集群。

详细接入与以前的持久化验证见 [本地 PostgreSQL 说明](local-postgres.md)。

## 5. 跑一遍采购流程

先用管理员登录，完成一次基础配置：

1. 在采购工作台的“库存台账”登记物料，例如 `A-01`，数量应足够本次采购测试使用。
2. 在系统管理的“用户与部门”创建业务部门、采购员和经理；为新用户设置密码。
3. 在“角色与授权”创建采购角色，授予 `PurchaseOrder.read`、`PurchaseOrder.create`、`PurchaseOrder.submit`、`PurchaseOrder.cancel`，并给采购单设置适当数据范围。把角色分配给采购员。
4. 创建经理角色，授予 `PurchaseOrder.read`、`PurchaseOrder.approve`、`PurchaseOrder.reject`，为 `PurchaseOrder.approve` 填写审批额度 `ceiling`，并设置采购单数据范围。把角色分配给经理。
5. 在部门的“负责人”中选择经理。采购员属于这个部门，经理和提单人应为不同用户。

新用户默认没有角色，新角色默认没有能力，需要完成上述授权后才能操作业务。

然后体验业务：

1. 采购员登录，新建采购单，填写金额与物料明细，提交审批。
2. worker 根据部门负责人创建审批待办；经理登录，在“我的待办”或工作台审批待办中处理。
3. 最终审批通过后，采购单进入已批准状态，同事务反应创建库存锁。
4. worker 调用 fake ERP，返回并回写 `DEMO-…` 单号；同步情况可在系统管理的“第三方同步”查看。
5. 取消采购单后，异步反应释放库存锁；真实收货回调也有相应命令与释放流程。

金额超过 `50,000` 时，还会进入财务审批。需先创建编码为 `finance` 的角色并分配审批用户，配置相应审批能力及额度。首次体验可先使用低于该金额的采购单。

审批失败先看错误：没有待办可能是负责人未配置或 worker 未运行；`STOCK_SHORT` 表示库存记录缺失或数量不足；额度或职责分离失败会拒绝最终审批。异步失败和死信在“异步任务”查看，修复原因后再重放。

这个范例用于演示采购、审批和库存锁生命周期。`Inventory.available` 是演示台账数量，还没有实现完整仓库扣减、退货核算与真实 ERP 撤单补偿。数据库是真实 PostgreSQL；ERP 目前是 fake，`erp.ts` 的外部域名仍为示例地址，不能只把 `CAGE_STAGE` 改成 `prod` 就当作完成真实对接。

## 6. 图谱怎么读

在业务项目根目录执行：

```powershell
pnpm exec cage graph
# 如果默认端口被其他服务占用，可另选一个端口。
pnpm exec cage graph --port 15419
```

上面两条是二选一。图谱读取 domain 声明，不需要先启动数据库；服务只监听本机。

| 视图 | 适合看什么 |
| --- | --- |
| 对象与字段 | 默认视图；绿色表头卡片，查看中文字段、类型、必填与引用关系 |
| 业务流程 | 命令、事件、反应、审批之间如何协作 |
| 完整本体 | 所有声明节点与关系，适合进一步追溯技术细节 |

页面中的“业务对象”，框架术语叫**聚合**：把需要一起遵守业务规则的数据、状态和操作作为一个整体管理。例如采购单不仅有金额和明细，还有草稿、待审批等状态，以及提交、取消等命令。它不等同于一张数据库表。

常用操作：

- 点击字段或节点看详情与源码位置；拖动卡片表头调整位置，滚轮缩放画布。
- 点击连线、连线文字，或详情里的“解释”，查看**为什么连接、有什么用、箭头怎么读**。
- “聚焦关联”缩小到直接关系；对象字段视图中的字段聚焦仅显示该字段引用。
- 搜索支持中文名和英文标识，可以定位隐藏对象、字段和其他视图中的命令。
- 勾选“包含系统组织模型”查看部门、用户等对象。
- 修改 domain 后点击“重新抽取”，同步刷新图谱和规则问题；也可以下载原始 JSON。

例如 `PurchaseOrder.deptId → Dept` 表示采购单的部门字段引用部门；审批分支连接这个字段表示按该部门找负责人。**图谱连线说明声明关系，不是某一张采购单的实际执行轨迹。** 归属补充、查询文本匹配等推导关系会在解释中标明依据。

表卡片展示声明字段，不是数据库完整物理列清单。ref/hasMany/manyToMany 会显示多对一、一对多或多对多基数；集合关系标记为非主表列，连线解释实际外键或自动中间表。业务写法见[对象关系](ai/relations.md)。

中文名称可在 `cage.config.json` 的现有 `graph.labels` 中补充，保留其他配置：

```json
{
  "graph": {
    "title": "采购业务图谱",
    "labels": {
      "aggregate:PurchaseOrder": "采购单",
      "field:PurchaseOrder.amount": "采购金额",
      "command:PurchaseOrder.approve": "通过审批"
    }
  }
}
```

这是配置片段，不要用它覆盖整个配置文件。键是 `节点类型:节点 ID`，可从节点详情核对；显示名不改数据库表、命令路由、能力标识或影响分析哈希。

## 7. CLI 命令在哪里执行、结果在哪里看

除特别注明外，以下命令在**业务项目根目录**执行，即含有 `cage.config.json` 的目录：

```powershell
cd F:/cage/examples/purchase-admin
pnpm exec cage --help
```

框架仓库根目录没有这个业务项目的 domain，不能直接在那里执行 `cage gen` 期待生成采购契约。也可在仓库根目录使用 `pnpm --filter @app/purchase-admin gen`。

| 命令 | 做什么 | 去哪里看 |
| --- | --- | --- |
| `pnpm exec cage analyze` | 检查并抽取本体图 | 终端、`.cage/ontology.json` |
| `pnpm exec cage check` | 声明静态检查、图规则检查 | 终端错误码、位置、原因及修法 |
| `pnpm exec cage graph` | 打开图谱服务 | 终端显示的浏览器地址 |
| `pnpm exec cage gen` | 生成契约、清单、SQL、状态图、迁移草稿 | 见下方产物表 |
| `pnpm exec cage gen --check` | 检查契约和迁移是否与声明一致 | 终端；不补写生成物 |
| `pnpm exec cage impact --base-file .cage/baseline.json` | 对比保存的本体图 | 终端，可用 `--out` 保存报告 |
| `pnpm exec cage test --only project` | 只运行项目测试 | 终端、`.cage/test-results.json` |
| `pnpm exec cage test --only derived` | 只运行派生测试 | `generated/tests`、测试报告 |
| `pnpm exec cage test` | 运行派生和项目测试 | 同上，跳过用例单独计数 |
| `pnpm exec cage verify` | 类型、依赖、lint、图规则、生成一致性、托管区、预算、测试门禁 | `.cage/verify.json` 及测试报告 |
| `pnpm exec cage verify --skip-tests` | 只做不含测试的门禁 | 报告中 `complete: false`，不能当作完整验证 |
| `pnpm exec cage budget` | 检查体积、原语和 unsafe 预算 | 终端指标和问题 |
| `pnpm exec cage sync` | 更新 AGENTS.md 的框架托管区 | AGENTS.md；保留托管区外自有内容 |
| `pnpm exec cage sync --check` | 检查托管区是否需要更新 | 终端，不写文件 |
| `pnpm exec cage upgrade --dry-run` | 查看当前升级规则会改哪些文件 | 终端，不执行改写 |
| `pnpm exec cage init` | 用管理员连接准备账号和授权，自动填写 .env | 终端、项目 .env、已有数据库 |
| `pnpm exec cage migrate` | 执行尚未运行的迁移并更新安全层 | 终端、目标数据库 |
| `pnpm exec cage dev` | 启动本地开发进程、监听声明变化 | 终端和业务页面 |

`gen` 的主要产物：

| 路径（相对业务项目） | 用途 |
| --- | --- |
| `packages/contracts/src` | 前端类型、SDK 与 hooks；不要手改 |
| `.cage/ontology.json` | 本体图 JSON |
| `generated/routes.json` | 业务路由清单 |
| `generated/capabilities.json` | 能力目录 |
| `generated/sql/schema.sql` | 期望表结构 |
| `generated/sql/safe-layer.sql` | 安全视图、策略与函数 |
| `generated/diagrams/README.md`、`*.mmd` | 可用 Mermaid 渲染的状态图 |
| `db/migrations/000N_draft.sql` | 有结构变化时生成的迁移草稿；首次为 `0001_init.sql` |

`gen` 只生成文件；`migrate` 才执行数据库迁移。运行中的 `dev` 在 domain 变化后自动执行 `gen` 并提示审查迁移，**不会自动执行 `migrate`**。有表结构变化时审查草稿，再手动运行 `pnpm migrate`。

当前目录没有 Git，影响分析先保存改动前的图：

```powershell
pnpm exec cage analyze
Copy-Item .cage/ontology.json .cage/baseline-before-change.json

# 此时再修改 domain；不要用改动后的图覆盖基线。
pnpm exec cage impact --base-file .cage/baseline-before-change.json --format md --out .cage/impact.md
```

以后项目具有 Git 历史时，可改用 `--base <提交或分支>`。影响报告用于定位关联改动，不会自动修改业务代码。

`upgrade` 将框架依赖统一到当前 CLI 的版本，自动改写仅包含早期 `caller` → `invokedBy` 规则，不会自动迁移目录或业务数据。本地 `link:` 项目使用 `upgrade --codemods-only` 保留本地依赖。`sync` 当前只同步 AGENTS 托管区，不同步业务代码、模板或全部 CI 文件。升级到 `0.2.0` 前请阅读[升级说明](release-0.2.0.md)。

## 8. 开发自己的业务时改哪里

使用 Codex 等编程工具时，先让它读取生成项目根目录 `AGENTS.md`；项目内 `docs/ai/README.md` 是业务学习入口，`recipes.md` 按新增对象、审批、报表、第三方和导入导出给出步骤，`docs/errors` 按错误码排查。框架源码中的对应规范入口为[业务开发指南](ai/README.md)，无需让业务开发工具通读内核源码。

| 文件/目录（相对业务项目） | 修改内容 |
| --- | --- |
| `packages/domain/src/modules/purchase` | 采购对象、状态、命令、约束、事件、审批、查询和任务 |
| `packages/domain/src/modules/inventory` | 库存对象与库存锁 |
| `packages/domain/src/workflows/purchase-inventory.ts` | 同事务或异步反应、资源获得与释放标记 |
| `packages/domain/src/integrations/erp.ts` | 第三方连接器、出站和入站映射 |
| `packages/domain/src/index.ts` | 导出声明，供内核和抽取器发现 |
| `apps/api/src/main.ts`、`worker.ts` | 装配框架，不实现第二套连接和业务路由 |
| `apps/web/src/main.tsx`、`app` | 挂载 Provider、恢复会话、组合导航与模块 |
| `apps/web/src/modules/<业务>` | 页面、表单、专用 hooks 与样式；模块 index.ts 提供公开入口 |
| `apps/web/src/shared` | 与具体业务无关的共用 UI/hooks/工具 |
| `packages/contracts/src/aggregates/<聚合>`、`queries` | 生成 SDK，业务从 `@app/contracts` 公共入口使用 |
| `cage.config.json` | 项目路径、检查目录、图谱中文名称等 |

例如给采购单增加“备注”时，先修改对象字段，再修改需要接收备注的命令输入；检查 handler 是否需要赋值或转换，然后生成契约和迁移，最后修改前端表单。只加表单而不改命令输入，不能保证备注被接受和保存。

完整目录与依赖规则见[工程目录与代码组织](ai/project-structure.md)。新模板启用 `structure: modular`，`cage check` 与 `verify` 阻止 src 根目录平铺业务及模块依赖越界；已有项目可以整理后显式开启。公共 API、表名和能力点不因移动目录而改变。

建议开发顺序：

1. 声明字段、状态、命令和必要约束，使用模块顶层 `export const`，从 domain 入口导出。
2. handler 的读依赖放入 `reads`；写入走命令，外部调用走连接器。
3. 在项目目录执行 `pnpm exec cage check`、`pnpm exec cage gen`。
4. 有结构变化时审查迁移草稿，再执行 `pnpm exec cage migrate`；不要改写已经执行或发布的迁移。
5. 前端通过 `@app/contracts` 调用生成的 SDK，同时补上图谱中文名称。
6. 根据改动做必要的定向验证；提交或交付节点再执行完整 `verify`。

新增能力不应自动授给生产角色，应在管理页明确授权。注释说明业务意图、约束和关键时序，避免为没有实际业务需要的情况添加兜底分支。

## 9. 从模板创建独立项目

`0.2.0` 提供双模板选择和本文的已有数据库接入流程。通过 npm 创建可执行 `pnpm create @yss123/cage-app@0.2.0 my-app --template blank`。试用本地源码时先构建框架，目标目录必须尚不存在：

```powershell
cd F:/cage
node packages/cli/bin/cage.js create F:/my-cage-app --framework-path F:/cage
# 交互选择空白或采购示例；自动化可在命令末尾加 --template blank 或 --template purchase。
cd F:/my-cage-app
pnpm install
Copy-Item .env.example .env
# 编辑 .env：只填写 CAGE_ADMIN_DATABASE_URL，连接已有数据库。
pnpm exec cage init
pnpm build:app
pnpm gen
# 审查迁移后执行：
pnpm migrate
pnpm exec cage bootstrap --credentials-file .cage/admin-credentials.json
pnpm dev
```

数据库配置文件就是 `F:/my-cage-app/.env`，每项含义见同目录 `.env.example`。生成项目通过 `link:` 使用 `F:/cage/packages/*`，本地框架目录需要保留。

空白模板保留真实登录、组织权限、系统管理、API/worker、数据库配置及 AI 学习材料，只生成组织和系统表；采购模板包含完整采购业务。省略目录可交互输入，Ctrl+C 可取消；CI/管道中必须同时指定目录和 `--template`。选择在写文件前完成，不会先生成采购再删代码。

同时运行多个应用时，按已有数据库实际地址填写连接，并将 `CAGE_WEB_PORT`、`PORT` 分别设为不同空闲端口，例如 `15174`、`3001`。修改应用端口不需要创建新数据库。不同应用若使用同一数据库，须先评估同名表和迁移是否冲突。

新项目的管理员凭据通过显式 bootstrap 的新受限文件交付，交付后移除。需要第二个图谱时运行 `pnpm exec cage graph --port 15419`。

发布版创建入口为 `pnpm create @yss123/cage-app my-app`；它使用 npm 中的版本，不能自动获得尚未发布的本地修改。发布步骤见 [npm 发包说明](npm发布说明.md)。

## 10. 常见问题与验证口径

| 现象 | 优先查看或处理 |
| --- | --- |
| `cage` 无法执行或找不到 `@yss123/cage-*` | 使用 `pnpm exec cage`；确认已安装依赖、构建框架；独立项目确认本地 link 路径存在 |
| 找不到 domain 入口 | 进入含 `cage.config.json` 的业务根目录；核对 `domain` 配置 |
| 数据库连接被拒绝 | 检查数据库服务、项目 `.env` 中的主机/端口，以及网络是否可达 |
| 数据库认证失败 | 核对 `.env` 中的数据库名、账号、密码；密码特殊字符需 URL 编码 |
| 迁移提示权限不足 | 使用管理员连接运行 `pnpm exec cage init`，核对目标库授权 |
| `CAGE-INIT-002` | 集群已有 Cage 账号，需复用原 APP / READ / MIGRATE 凭证，不要重置其他项目密码 |
| Web 报端口权限错误或占用 | 调整 `.env` 的 `CAGE_WEB_PORT`，重启 `dev`；API 端口用 `PORT` |
| `CAGE-GEN-001/002` | 运行 `gen` 并审查生成差异，不直接手修契约 |
| `CAGE-PAIR-002` | 某条离开持有资源状态的路径没有释放资源；检查对应事件和反应声明 |
| 有角色仍显示 403 | 同时检查具体能力、角色是否启用；经理还需审批额度 |
| 单据存在但返回 404 | 也可能是数据范围外；检查角色范围与单据所属部门/提单人 |
| 审批通过后 ERP 单号未出现 | 检查 worker、第三方同步记录及死信；本地应为 `CAGE_STAGE=fake` |
| 图谱改动未出现 | domain 是否从入口导出、是否抽取报错；点击“重新抽取” |

完整错误码册见 [docs/errors](errors/README.md)。反馈问题时保留错误码、终端提示或 `requestId`，便于追查对应审计与日志。

按变更范围选择验证，不必每改一处文案就运行所有测试：

| 场景 | 建议命令及位置 |
| --- | --- |
| 声明或生成物改动 | 业务根目录：`pnpm exec cage check`、`pnpm exec cage gen --check` |
| 业务行为改动 | 业务根目录：必要的项目测试；`pnpm exec cage test --only project` 会运行项目测试集合 |
| 业务完整交付 | 业务根目录：`pnpm exec cage verify`；或框架根目录 `pnpm example:verify` |
| 框架改动 | 框架根目录：`pnpm build`、必要回归；Docker 全部框架测试为 `pnpm test:docker` |
| 框架预算 | 框架根目录：`node packages/cli/bin/cage.js budget` |

本次文档核对没有重跑上述构建和测试。此前记录为框架 **88 个通过**、采购范例 **91 个通过及 10 个跳过**；跳过不等于通过，完整门禁执行结束也不等于所有业务路径都被覆盖。当前未交付项及生产验收边界统一列在 [设计实现对照表](design-coverage.md)。
