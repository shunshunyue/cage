# Cage 原生 OA 能力路线图：参考 Flowable

本文包含历史设计和验收记录，其中角色审批额度机制现已移除；审批分支由业务需要决定，历史结果不代表当前实现。

本文记录 Cage 原生审批引擎的能力建设路线、Flowable 官方资料对照，以及人员流转、流程时效和结构化并行的实现与验收边界，供框架维护者设计与评审使用。业务应用应以 [框架学习入口](../development/README.md)、已导出的 API 和当前版本实现为准，不能把本文中的规划名称当作可调用 API。

调研日期：2026-11-07。建设方向为保留 Cage 的 TypeScript 声明、命令写入、权限、审计、本体与 worker 执行模型，参考成熟引擎的业务语义，分批补齐 OA。本文不承诺完整 BPMN/CMMN/DMN 标准兼容，不引入 Flowable Java 运行时，也不把业务图展示当作流程执行器。

## 1. 对标范围与资料依据

Flowable 不是一个“审批页面组件”，其能力包括流程、案例、规则三个开源引擎，以及建模、表单、运营管理等产品层。对标时要分别看执行语义、运维能力和用户界面。

| 类别 | 解决的问题 | 本次核对的官方资料 | 对 Cage 的意义 |
| --- | --- | --- | --- |
| BPMN 流程引擎 | 有明确执行路径的人工/自动任务、网关、事件、子流程、多实例 | [BPMN Constructs](https://www.flowable.com/open-source/docs/bpmn/ch07b-BPMN-Constructs)、[引擎 API](https://www.flowable.com/open-source/docs/bpmn/ch04-API) | 先补任务生命周期，再扩展并行执行和事件等待 |
| CMMN 案例引擎 | 路径不完全预先固定的案件、理赔、工单、调查和材料补充 | [CMMN 1.1 Constructs](https://www.flowable.com/open-source/docs/cmmn/ch06-cmmn) | stage、milestone、进入/退出条件、重复和人工激活是独立问题，不应伪装成顺序审批 |
| DMN 决策引擎 | 输入事实到输出决策的可维护规则表 | [DMN 1.1 Introduction](https://www.flowable.com/open-source/docs/dmn/ch06-DMN-Introduction) | 金额路由、选人、额度和风险规则可逐步数据化，业务硬约束仍由命令验证 |
| TaskService | 任务分配、领取、委派、归还、完成、身份关系 | [OSS TaskService Javadoc，2025.1 文档](https://developer-docs.flowable.com/javadocs/flowable-oss-javadoc/2025.1/org/flowable/engine/TaskService.html) | 区分转办、委派、归还和领取，避免把它们都实现为修改 assignee |
| 实例迁移 | 在途实例从旧定义迁移到新定义，验证活动映射 | [Process Instance Migration](https://www.flowable.com/open-source/docs/bpmn/ch08-ProcessInstanceMigration) | 定义版本与实例版本要分开；已有实例不能随代码发布静默换路线 |
| 开源与商业产品 | Apache 2.0 引擎与企业平台、管理和建模产品的边界 | [Flowable Open Source](https://www.flowable.com/open-source) | 比较能力，不把商业 UI、连接器和管理平台全部算作开源引擎默认交付 |

上述资料本身有版本边界。尤其 DMN 1.1 指南写明当前讨论的是 decision table，表达式使用 JUEL，并明确不支持该指南所述的 (S)-FEEL；不能从“支持 DMN”推断实现了所有版本的 FEEL 或全部决策表达式。BPMN Constructs 也列出了部分构造的具体限制，不能照抄宣传页得出“所有标准语义均支持”。正式实施某个兼容功能时，应固定 Flowable 版本及相应规范再次核对。

Flowable 官方开源页把 BPMN、CMMN、DMN 引擎列为 Apache 2.0 开源项目，同时单独介绍企业平台的细粒度权限、内容管理、可定制 UI、Control 运营仪表盘与 Inspect 可视化调试。Design 存在免费建模入口；免费使用不等于整个企业产品开源。Cage 当前只借鉴语义与能力分层，不承诺复刻这些商业产品。

## 2. OA 能力矩阵

“基线”指本路线图建立时已有实现；第一批和第二批记录见第 7、8 节，后续时效与结构化 AND 并行进展见第 9、10 节；“后续”仍是规划。各批历史验证只证明当时选定范围，不累加成全部流程能力验收。下表更新当前能力状态，覆盖业务类别，不是 BPMN 规范的逐条一致性认证。

## 3. 分批顺序与完成标准

### 第一批：人工任务人员操作和可靠历史

纳入：转办、单层委派归还、当前节点并行必签、任务 revision、不可覆盖的动作流水、HTTP/SDK 接入、兼容迁移与定向回归。由人工 `step` 的 `actions` 明确选择启用，缺省全部关闭，已启动实例使用自己的声明快照。

第一批交付时未含候选领取、前后加签和人员操作界面，这些后续进展记录在第二批。自然分钟 SLA 的后续进展见第三批，结构化 AND 并行进展见第 10 节；指定节点退回、可视化设计器和完整 OA 工作台仍未实现。

完成标准：普通单人、any、all、AI 人工接管、取消重提、最终命令失败均保持既有语义；新动作在跨租户、无权限、旧版本、重复目标和并发冲突时明确拒绝；历史记录与状态变化共同提交或回滚。

### 第二批：人员规则、候选领取和操作体验

已实现的人员核心：候选池 claim/unclaim、`approver.field`、前/后加签及持久 waiting 依赖、SDK/HTTP、Admin 与采购待办的领取/释放/委派归还及等待视图。采购 view 进入查询参数；新的字段或候选节点开启时检查同租户 active 用户，候选领取时继续实时核验规则、批准/read 和范围。

采购范例后续已接入发起转办/委派/三种加签的协作名录选人器及分页人工历史 UI，并通过真实账号和隔离业务库浏览器验证。通用框架本批补站内流程提醒；受限岗位/组织策略、无可用人员的通用受控恢复、抄送和代理时间段仍待完成。

核心验收标准：选人和领取不授予权限；未领取任务的候选资格变化即时影响可领取名单，八人并发最多一位持有人；已经领取后撤去候选身份不自动取消职责，实际决定/释放仍需业务权限；前后签不能被 any 抹掉，激活增加 revision；旧直派任务及旧实例政策保持含义。38 项新增回归与既有 106 项相关回归已通过，具体记录见第 8 节。

### 第三批：时间、退回和流程运营

当前先实现框架时效部分：`approvalOperations()` 通过 runtime 接入现有 worker，`step.sla` 配置人工节点自然分钟总时限，`route.reminders` 配置申请人和持久冷却。公共 HTTP/SDK 和通用 Admin 提供截止时间、我的申请、催办、临期/超时站内提醒及已读。实现位于 approval/admin/client/HTTP 包，采购项目不承载这些通用功能，只在独立验收装配中接入短时限。具体协议和权限边界见 [审批指南](../development/guides/approvals.md)。这不表示第三批其余能力已完成。

补持久 SLA timer、提醒/催办、超时升级、业务日历、指定节点退回、任务取回及授权的人工恢复。超时不能简单写成内存 setTimeout，提醒失败不能导致审批通过，重试不能重复升级或发多份通知。

完成标准：重启、双 worker、取消与 timer 同时发生、夏令时/时区转换、离职/撤权等场景有明确结果；所有恢复通过受控入口和审计，不指导运维 SQL 改状态。

### 第四批：并行、子流程和可靠长流程

当前先实现有界结构化 AND 并行与汇合，分支内部支持多步、条件和嵌套并行，实例冻结依赖及路由内容指纹，旧快照保持顺序语义，见第 10 节。事件等待、多实例、子流程、完整定义发布、受控迁移和补偿仍是后续工作，需复用现有事件/连接器/命令并分别定义可靠性边界。

完成标准：并行任何分支重试不重复推进；join 等待的集合明确；取消能关闭所属执行范围；迟到消息不能恢复旧轮次；远端未知结果必须先核对，不能假定补偿必定成功。

### 第五批：规则、案例和可视化发布

按实际客户需求增加决策表、规则版本及测试样本；案件型需求再引入 stage/milestone/sentry 等案例概念。可视化设计器生成受限声明或中间表示，进入与代码相同的校验、授权、发布和审计链。

完成标准：界面保存不等于发布；发布前能显示影响和迁移风险；实例绑定具体版本；设计器不能生成绕开领域命令的 SQL 或任意网络执行。

## 4. 第一批详细语义与不变量

以下保留第一批任务流转的设计约束；第二批新增候选和前后签的具体语义见第 5 节。方法名和字段只有在公开入口导出且通过验收后才是可用 API；本文不能代替实现说明。

### 4.1 把任务状态、分配与委派分开

| 维度 | 设计含义 | 不应混淆的情况 |
| --- | --- | --- |
| task.status | pending、approved、rejected、returned、skipped/cancelled 等任务结果 | 转办不是审批通过，归还不是 returned 业务结论 |
| assignee | 当前可操作的真人用户 | 与最初选中的人、最终签署责任人可能不同 |
| owner | 本次委派需要归还的原执行人 | 转办为责任移交，不应残留旧 owner 形成虚假归还路径 |
| delegation state | 无委派、等待归还、已归还 | 等待归还不能直接 approve/reject/return |
| task kind | original 或 additional | additional 是必签票，不继承 any 的任一通过语义 |
| revision | 每个任务的单调递增版本 | 不是业务单据 version，也不是实例 current_step |

委派流程为：原执行人 A 持有 pending 任务 → A 委派给 B，保存 owner=A、assignee=B → B 提交处理说明并归还 → assignee 回到 A → A 再作审批决定。B 的归还只记录完成委托，不给单据审批结论。委派待归还期间，本批禁止继续转办、委派和加签，避免形成没有定义归还顺序的嵌套链。

转办为 A 将任务直接交给 B：B 变成当前执行人，A 失去决定该任务的资格；B 后续决定仍使用 B 自己实时拥有的能力、范围及额度。转办原因与审批意见分别留存。

### 4.2 输入和动作启用

- 只有人工步骤显式声明 `actions: { transfer: true, delegate: true, addSign: true }` 的对应动作才可用；未写、旧实例快照没有 actions、AI 节点未提供此声明都视为未启用。
- 新人员动作携带非负整数 `expectedRevision`、1–1000 字的非空原因；转办/委派携带单个目标用户 ID，加签携带 1–20 个用户 ID。
- 空白原因、重复 ID、自转办/自委派、自加签、跨租户或停用用户要明确拒绝，不静默去重、截断或跳过无效目标。
- 一批加签先完整验证全部目标，再共同创建；不能留下“部分目标失败但仍成功加了另外几人”的隐式结果。
- additional 任务不能继续加签；本批不暴露任意修改 task kind、owner、delegation state 或实例步骤快照的接口。
- revision 防止旧操作覆盖新分配。审批决定接口如保留兼容的无 revision 调用，应明确其边界，不能声称所有旧页面决定都受到任务版本保护。尤其 A→B→A 的转办链会形成仅比较 assignee 无法发现的旧页面问题。

### 4.3 权限与责任

动作发起者必须是当前任务合法执行人，任务所属实例仍运行且处于当前步骤。每个接收人必须属于同租户、账号 active，并且实时拥有此单据的 read 能力/范围和对应审批能力。流程选人、转办或加签不产生新的角色授权，也不继承发起者的额度。

最终单据结论继续由 `applyOutcome` 调领域命令，复核状态、提交版本、职责分离、额度与不变量。中间节点的操作通过不能被描述成这些最终硬约束已经全部验证。

如果沿用现有“最后实际审批人承担最终结论身份”的规则，最后完成的 additional 审批人也可能成为最终结论的真人身份。因此此人的额度不足、职责分离不满足或权限被撤销时，最后决定与状态/历史必须共同回滚，不能替换成较早审批人的身份来偷偷通过。若产品希望原审批人始终承担最终签署，必须另设计“加签结束后回原审批人确认”，不能在后台隐式冒用。

同一节点的多人职责应防止被人员操作压缩成一人多票。至少拒绝目标与当前未决任务执行人/委派 owner 重复；对于要求独立会签的策略，还应拒绝本节点已签署的人再次承担另一票。将来允许同人多身份时，需要显式规则和审计，不能由普通转办偶然实现。

委派归还时原 owner 已停用或已失去权限，应有明确拒绝与恢复边界。本批没有管理员恢复接口时，文档必须说明它尚未覆盖，不能自动归还到无资格用户并宣称流程仍可顺利完成。

### 4.4 加签与 any/all 的完成条件

令 O 为原始任务集合，A 为加签任务集合。只有无驳回/退回、无待归还委派，并且满足下述条件时才推进：

- any：O 中至少一票已通过，且 A 中全部已通过。
- all：O 与 A 全部已通过。

any 第一位 original 通过后，其余 original 可变为 skipped，additional 仍保留并逐个处理。原审批人通过不能批量跳过 additional；additional 先完成也不能替代至少一票 original。所有 original 被跳过但没有任何 original 批准属于非法结果。

任一有权且当前可决定的任务驳回或退回，走对应领域结论；结论成功才关闭其余未决任务。若最后结论命令失败，当前决定、其他任务关闭和动作历史共同回滚。流程取消、重提关闭旧轮次和 any 跳过，都必须使旧任务版本失效，并保持历史可追踪。

### 4.5 事务、并发、重试和审计

按一致顺序锁定实例再锁任务，在锁内重新检查租户、process、实例状态、current_step、任务状态、assignee、委派状态与 expectedRevision。锁前预读只可帮助定位实例，不能作为最终授权证据。涉及多个任务时使用稳定顺序，避免同一节点的操作采取相反锁顺序。

任务状态变更、revision 增加、新任务创建和动作流水追加必须在同一 PostgreSQL 事务里提交。追加记录至少关联租户、实例、步骤、任务、动作类型、真人 actor、前后执行人/owner、前后 revision、原因与服务器时间；多目标加签要能关联一次操作与新建任务。敏感单据正文、密钥或完整授权上下文不应塞入原因或动作快照。

动作历史只能追加。审批意见保留在原决定记录中，转办/委派原因不可覆盖原意见。取消/跳过等系统动作需要能区分系统触发与真人发起，并能追溯到相应实例/业务事件。没有既往动作证据的历史任务迁移时只建立基线，不伪造它们发生过转办。

历史读取仍需业务对象当前 read 能力和范围，不能因为用户曾经处理过任务就永久获得单据访问权。新任务列表/动作响应也不能返回超出原有安全投影的完整领域数据。

revision 冲突可以防止重复修改，但不等于幂等重试回执。若请求已提交而响应丢失，同 revision 重试可返回冲突；客户端应重新读取任务/动作历史核对结果。只有实现了明确的动作幂等键和回执持久化后，才能承诺重试返回同一结果。

## 5. 第二批已经实现的人员与签序语义

### 5.1 字段选人与开启检查

`approver.field('reviewers')` 读取实例保存的 routable 变量，支持单个 UUID 或 1–200 项 UUID 数组并去重；不是执行任意表达式。字段必须属于绑定聚合、不是 hidden 且列入 routable，否则声明报 `CAGE-APPR-001`。缺失/null 解析为空候选并在开启时报 `CAGE-APPR-007`；空数组、非法 UUID、非法类型和超长数组报 `INVALID_INPUT`。

字段选人和 candidate 节点开启时检查全部选中的用户属于当前租户且 active，不合格则整批失败，不删掉无效目标后继续。旧固定用户/部门负责人 direct 开启行为保持兼容。账号有效性不等于有业务批准/read/范围，实际领取与决定仍重新授权；无可用人员没有通用恢复操作，修复组织配置或应用撤回重提需走其合法入口。

### 5.2 单项候选任务的领取和释放

`step(title, selector, { assignment: 'candidate' })` 只建立一项无人持有的任务，不能与 `mode: 'all'` 配合；默认 direct 仍逐人建票。claim/unclaim 由 assignment 独立启用，不需要新增 actions 属性。接口为 `engine.candidateTasks(userId, tenantId)`、`engine.act(..., { action: 'claim' | 'unclaim', expectedRevision, reason })`；SDK 为 `approvalCandidateTasks()` 和已有 `approvalTaskAction()`，HTTP 为候选列表及任务 claim/unclaim 路由。

候选规则保存在实例步骤中；角色/部门成员在列表与领取时按当前组织解析，field 使用提交快照。claim 在实例→任务锁内检查未分配、当前步骤、提交版本、候选身份、active、批准/read/范围及本人没有同节点其他票。两个或更多候选竞争只能一人成功，已被别人领取可返回 NOT_FOUND，仍未分配的陈旧 revision 返回 CONFLICT。展示列表不预占任务，未领取不能决定。

unclaim 只允许 candidate 当前持有人，且仍需批准/read/范围；已经退出候选角色不阻止合法释放，也不自动取消已承担职责。candidate 转办给有权限的非候选人后仍保持 candidate 属性，新持有人可按规则释放。待归还委派、waiting、非当前步骤、已结束，或存在未完成前/后/并行子票时不能释放。已完成子票和历史保留，已签过子票的人不能再领取原票。

候选池当前无人可领时返回空，不扩大到管理员或自动批准；尚无管理员强制释放/改派恢复入口。候选列表逐流程最多扫描最近 200 项，再按规则/权限过滤，当前没有游标分页，不能把空结果作为所有历史任务都处理完毕的证明。

### 5.3 前后加签与 any/all

`addSign` 新增可选 `placement: 'parallel' | 'before' | 'after'`，缺省 parallel。新 step 在 addSign=true 时自动保存 signPositions 三种允许位置；请求必须符合实例快照。每项新追加票保存父任务及签序，多目标彼此并行，每节点累计最多 20 位，additional 不能再加签。

| 位置 | 初始状态 | 激活依赖 |
| --- | --- | --- |
| parallel | 父票和子票 pending | 原有全部追加票必签语义 |
| before | 父票 waiting，子票 pending | 所有前签批准才恢复仍 waiting 的父票 |
| after | 父票 pending，子票 waiting | all 由自己的父票批准后激活；any 由任意原票批准后激活 |

waiting 不能决定或管理。any 另一原票先胜出时，其他 pending/waiting 原票 skipped，但全部 additional 保留；所有 waiting after 激活，before 后续完成不复活已 skipped 的父票。all 只激活当前批准父票自己的 after，并继续等待其余原票和追加票。

恢复父票和激活后签均 revision++，使等待页面保存的版本失效。拒绝/退回的结论命令成功后，以及取消/重提时，pending 和 waiting 都关闭。最后实际批准人承担领域结论身份，后签超额度等失败会回滚本次决定、激活和记录，之前已提交的票保留。

### 5.4 迁移、界面和助理边界

新增系统迁移 `cage:approval_task_stages_002`，在 actions_001 之后增加 assignment、parent_task_id、sign_position，并仅允许 candidate 持有人为空。旧任务仍 direct，旧原票/并行追加票的父与签序为空；旧任务不合并，旧快照不自动增加 actions/assignment/signPositions。已有 addSign=true 但没有 signPositions 的旧节点仅允许 parallel，before/after 拒绝；没有 addSign 政策仍不能加签。公开任务摘要提供 signPositions 供界面判断，新增加签票保存父任务/签序。先 migrate，再统一切换 API/worker，已发布 DDL 和迁移不改写。

Admin 与采购页已有本人/候选/等待视图、领取、释放、受托任务归还及普通审批。采购页通过 `view=candidates`、`view=waiting` 保留视图；waiting 无决定入口。采购后续补齐协作名录选人器、转办/委派/加签和人工历史；框架时效部分在通用 Admin 提供申请催办和提醒。页面存在不等于业务路由已启用，部署时仍需独立验收。

AI 助理的 approval_tasks 只查本人 pending，approval_decide 继续带原任务版本确认并执行；没有候选领取/释放或人员管理写工具。新操作通过 SDK/HTTP 调用，不能在文档中假定助理已经支持全部 OA 管理动作。

## 10. 结构化 AND 并行进展（2026-11-07）

框架公开 `parallel(title, ...branches)` 与 `branch(title, ...nodes)`，支持多条具名分支从共同入口开启、每条分支独立顺序推进、全部实际展开的分支通过后再进入后继。分支可嵌套条件和并行组，人工/AI 节点及既有候选、转办、委派和前后加签继续使用同一引擎。采购只作为接入验收载体；执行模型、协议、Admin 和图谱渲染均由通用框架实现。

| 方面 | 已实现语义及边界 |
| --- | --- |
| 执行与并发 | 实例锁内按持久前驱完成状态创建就绪节点，既有 `(instance_id, step)` 唯一键防止重复开启；同次推进中一个新节点开启失败会回滚整个本次事务，不保留部分分支入口 |
| 条件与结构 | 条件只在启动时求值；条件全部跳过的分支不留下等待票，整个路由为空则拒绝启动；最多 128 个办理节点、512 个结构节点、8 层容器，每组 2–16 条名称唯一的分支 |
| 结论与取消 | 任一分支拒绝/退回或业务取消会关闭整轮活动节点与 pending/waiting 任务；全部分支通过后才继续。实际最后办理人仍承担领域结论身份，不能绕过额度、职责分离或状态约束 |
| 持久化与兼容 | 执行元数据 `execution.schema/dependsOn/branchPath/definitionVersion` 复用实例 steps JSON，无新增并行 DDL 迁移；没有元数据的历史快照按相邻顺序执行，不随代码更新换路线 |
| 定义指纹 | definitionVersion 为流程名、路由节点及催办政策等声明内容的 SHA256 指纹，不包含领域命令实现；不是完整的定义版本发布、回滚、命令版本绑定或在途迁移 |
| SDK 与历史 | currentSteps 表示完整活动集合，currentStep 仅为最小活动索引兼容摘要；任务/步骤携带 branchPath，历史携带 dependsOn，申请 activeSteps 提供逐节点名称与截止时间 |
| 时效与催办 | 每个节点从实际开启时计时，各分支独立 SLA；催办覆盖全部活动节点、共享实例冷却，必须携带完整排序 expectedSteps；recipientCount 按任务/接收人配对计数，不是去重人数 |
