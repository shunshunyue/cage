# 框架教学的行为评估

本文件供 Cage 框架维护者评估 Skill，不是客户项目的业务需求，也不作为 agent 默认学习材料。正文唯一来源为 `docs/development/skills/cage-development/SKILL.md`。评估关注实际行为，文件结构校验和编译通过不能证明模型已经学会。

## 固定输入，保留独立判断

每次使用新的隔离目录和无本次设计讨论历史的 agent 会话。提供当前版本脚手架、对应 Skill、下面选中的需求，以及已授权的测试环境。不要把参考答案、怀疑的错误或上次评估结论一起交给被测 agent。模型、版本、宿主、框架提交和任务输入都写进评估记录。

需要真实数据库时使用独立测试环境和受限测试账号；需要外部系统时提供受控 fake 或明确授权的测试服务。未具备相应条件的任务记为未执行。不要修改客户项目、生产权限或向真实第三方发送测试业务。

## 基础任务集

| 编号 | 给 agent 的需求 | 维护者验收依据 |
| --- | --- | --- |
| A | 新增部门通知，发布人可以修改和撤回，同部门可读，其他部门不可读；有列表与详情 URL | 聚合/动作边界、真实保存读取、归属和直接请求隔离、刷新/深链接 |
| B | 在已有业务中增加归档，归档后不允许修改，保留历史记录 | 复用声明、from/to、旧状态受保护、生成/迁移一致，未扩大重构 |
| C | 为成员管理技能关联，技能目录分页，关联需要独立查询；只允许操作有权访问的两侧对象 | 正确选择关联原语、分页不覆盖完整集合、两侧授权、无重复纯中间表实现 |
| D | 申请提交后由部门负责人决定，申请人不能审批自己，撤回结束待办 | 真实组织与能力配置、待办决定、结论命令、拒绝路径与取消链 |
| E | 为业务记录增加 PDF 附件，保存后能授权下载，其他主体不可下载 | 上传字节、文件 ID 绑定、下载内容一致、范围拒绝与失败展示 |
| F | 完成业务后通知外部测试系统，响应延迟/重复投递不会造成重复业务处理 | 连接器与回写命令、可验证的幂等策略、未知结果处理，明确 fake/真实验证边界 |
| G | 提交成功后没有待办，请定位并修复 | 由维护者预置漏导出、停 worker 或无匹配审批人之一；查到实际断点，保留约束与已有状态 |
| H | 只改已有列表的列名和间距 | 修改范围匹配需求，不新建聚合、权限、审批或无关基础设施 |

扩展任务覆盖 query/报表、导入导出、job、原生 AI 和资源释放；先保证基础任务能稳定完成。更换业务名和表述检查迁移能力，不把具体案例写成所有项目的固定流程。

## 多轮协作任务

评估 agent 能否阅读后主动提出疑问、给出有依据的建议，并将用户选择落实。以下“维护者验收依据”不提供给被测 agent；只提供需求、原始文档和项目。按本次变更选择相关任务，不要求每次文档编辑都运行整个任务集。

| 编号 | 给 agent 的需求与原始材料 | 维护者验收依据 |
| --- | --- | --- |
| I | “做一个设备借用流程，负责人批准后能领用，归还时要检查。”不提供负责人来源、检查人或异常归还规则 | 主动发现影响当前设计的缺项，用业务语言提出选项、影响和推荐；不自行发明审批人或异常关闭规则，也不要求用户先选择原语 |
| J | “按这两份制度完善部门通知。”一份规定仅当前部门可见，另一份规定包括下级部门；当前代码只覆盖当前部门，用户未指定哪份制度优先 | 引用实际冲突，查清当前范围，解释两种可见性的影响，让用户选择；不因代码已实现某一种就当作目标，也不修改明确的其他规则 |
| K | “按项目分组限制记录可见范围，按附件接入。”附件使用了与安装版本不符的范围 API 写法 | 先核对公开签名与当前范围能力，指出材料中的问题；不让用户猜 API 是否存在，不编造接口；若确有缺口，说明可行方案与业务影响后让用户选择 |
| L | 先给出含多个疑点的需求；在 agent 提问后只回答其中一部分，后续再改变一项已确定规则 | 已答事项保留，未答事项仍待定，推荐不冒充选择；继续独立工作且不重复提问；规则变化落实到受影响的声明、页面和验收，可选改进不阻塞已明确任务 |

维护者事先保存每个任务的用户回答脚本和业务依据，按实际问题提供相应答案，不把完整答案提前交给 agent，也不临时迎合它给出的选项。脚本需允许等价的分批提问和用户补充其他方案；任务 L 明确记录哪一次回复故意遗漏、哪一次修改旧决定。用户模拟回复只能代表该隔离评估场景，不能作为真实项目的业务决定或操作授权。

保留实际提问、建议、用户回复、后续修改和验收结果。检查问题是否有来源和影响、选项是否可行、推荐是否有依据、选择是否落实，以及实现过程中出现的新疑问是否继续提出。不能按提问数量评分：少问但猜规则、多问却忽略答案都不合格。只检查文本或演练首轮对话时，明确未验证实际实现与验收，不计为完整任务通过。

## 核对编码前的判断

对涉及业务规则的任务，保留首个业务代码修改前的需求理解和实现映射，并与实际修改的先后顺序核对。映射需要连接用户已确定的规则、查证过的框架能力或现有声明、受影响模块和可观察的验收；只有“写后端、写页面、跑测试”的计划不算完成映射。不要把事后补写的解释算作编码前已理解。

结合任务 A–G 和 I–L 检查：是否优先复用现有模块；是否实际读取了相关能力/签名及前提；是否把待定事项实现为未经选择的规则；是否按映射完成了真实契约和服务端行为；最终验收是否回到用户选择。任务 H 可用一句话说明列名和间距的修改范围，不应为轻量改动引入业务建模或一轮技术方案批准。

## 记录结果并改进教材

每项分别记录“发现/读取 Skill”“需求理解”“疑点与建议”“用户选择的保留与落实”“编码前实现映射”“选择正确能力”“实际接入”“业务结果”“失败路径”“交付如实”是否通过，以及对话、请求、代码位置、运行结果等依据。无需澄清的任务相应项记为不适用；不使用模型自评作为通过证据，未执行单独列出，不能折算为通过率。

失败时定位原因：入口未加载、概念理解错误、疑点未提出、建议无依据、擅自决定业务、重复确认、忽略用户答案、未查证即编码、映射与实现脱节、能力选择错误、签名/前提缺失、实现遗漏或验证遗漏。针对原因修改对应章节/示例；不要为单次案例增加全局规则。重新运行受影响任务，并保留其他任务的回归记录。

不同宿主和模型分别执行，不从某一个 agent 的结果外推“所有 agent 都支持”。当前自动门禁 `pnpm docs:check` 验证分发与链接，`pnpm docs:examples` 验证入门课声明和页面能使用当前生成契约；它们都没有启动独立 agent，也没有替代真实数据库和浏览器验收。
