## 实际发现并修复的问题

1. 原有 `AnyCommand` 容器类型违反 handler 参数逆变要求，带明确 `reads` 的命令无法作为审批命令使用。容器擦除泛型，`command()` 调用处仍保留具体输入和依赖类型。
2. 已执行迁移被改写时，迁移器现在先核对历史校验和，再执行任何新迁移；拒绝修改历史。新增两个真实数据库回归用例。
3. Windows Git 的 LF/CRLF 转换曾造成未变化的命令被影响分析误报；哈希现在统一换行。Git 基线提取使用临时 worktree，不切换当前分支，并清理自己创建的依赖链接。
4. 已审批采购单立即取消时，晚到 ERP 回写原先会进入死信并堵住解锁。非新建命令现在可显式声明 `to: null`，在允许的 `from` 状态中仅更新字段；内核保留加锁读出的状态，仍检查权限、版本、不变量并写审计。图抽取按各个起始状态生成自环。取消和收货两种晚到回执均有真实数据库回归用例。
5. 测试退出码与 JSON 结果双重校验；故意注入失败用例验证门禁返回 1，临时用例随后移除。跳过用例单独报告。
6. 依赖审计发现 Vitest/tinypool 和 `@fastify/static` 的已知漏洞；分别升级到 Vitest 4.1.12 和 `@fastify/static` 10.1.8，并移除 admin 的无用依赖。
7. 根目录 `example:verify` 原先被 pnpm 解释为不存在的脚本，却返回成功；已改为调用示例现有的 `verify` 脚本，验收以实际门禁和报告为准。
8. Docker 实跑发现并行测试会竞争集群级角色初始化；testkit 改为在共同管理库上取得咨询锁，去掉简单重试，并用八个并行测试库回归验证。Turbo 显式传递测试连接变量，防止被严格环境过滤后意外使用内嵌库。
9. Docker 启动后 Windows 将 5173 列入保留端口；Web/API 端口现可配置，本机 Web 使用 15173。内核仍统一管理实际数据库连接，项目仅提供配置。

## 本体图谱工作台

- 新增 `cage graph [--port 15418]`，随 CLI 发布本地 Web 页面；支持聚合/类型筛选、全图搜索、节点拖拽、画布缩放、关联聚焦、源码位置、规则问题展示和原始 JSON 下载。
- 每次“重新抽取”由新进程加载 domain，解决 ESM 缓存导致依赖声明未刷新的问题；抽取失败会明确提示，并保留上一张成功快照。
- 中文业务名为主、英文标识为辅。声明 description 自动复用，项目通过 `graph.labels` 补充/覆盖显示名。采购范例 100 个声明节点全部配置中文名，状态、调用身份和常用约束也显示中文；显示文案不改变本体标识及哈希。模板已同步。

## 启动与使用

在框架仓库根目录执行：

```powershell
pnpm install
pnpm build
pnpm --filter @app/purchase-admin db:up
pnpm --filter @app/purchase-admin dev
```

本机采购工作台为 `http://localhost:15173`，系统管理为 `http://localhost:3000/admin/`。开发数据位于 Docker 命名卷，数据库凭证位于示例 `.env`，网页登录账号记录于 `.cage/local-access.md`，均不进入模板或发布包。`Ctrl+C` 关闭应用进程，数据库容器继续运行。首次初始化流程见 `local-postgres.md`。

创建独立业务项目：

```powershell
node packages/cli/bin/cage.js create ../my-app --framework-path F:/cage
cd ../my-app
pnpm install
pnpm build:app
# 与原示例并行运行时，先为新项目修改 devDbPort。
pnpm exec cage db setup
# 根据需要修改 .env 的 Web/API 端口。
pnpm exec cage db up
pnpm exec cage db init
pnpm dev
```

`upgrade` 当前只支持 0.1.0 目标版本和早期 `caller` → `invokedBy` codemod。未发布的本地项目使用 `upgrade --codemods-only`；正式升级在安装目标版本、生成并通过门禁后才报告完成。

完整端口配置与初始化说明见[使用说明](使用说明.md)。`db init` 仅用于独立新集群，已有集群使用普通 `migrate`。
