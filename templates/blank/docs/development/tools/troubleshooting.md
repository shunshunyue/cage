# 排错方法

## 先找第一个失败的边界

从真实用户动作开始，检查页面是否调用契约、请求是否发出、接口如何返回、持久记录是否改变，再看异步后续和页面刷新。页面显示成功但没有请求时，先修页面的数据来源；不要先改数据库或重写领域模型。

接口成功与流程完成分开判断。使用[诊断工具](diagnostics.md)按需要收集注册、构建、迁移、授权和执行记录；未取得的运行证据保持 unknown。保留失败输入与错误码，修复最小缺口后复验同一路径，避免同时改变多层而失去原因。

[返回学习入口](../README.md) · [错误码册](../../errors/README.md) · [HTTP 运行时错误](../../errors/runtime.md)

先保留完整诊断的 code、源码位置、reason/fix、requestId 或 outboxId。检查所在阶段，再修复原因；不要通过改业务状态、给全局权限、注释约束或禁用 lint 消除现象。

先执行 `pnpm exec cage doctor` 查看各阶段证据；异步动作按 requestId/outboxId/业务对象用 `cage timeline` 关联实际执行记录。能力、范围或调用身份不清楚时，有权诊断的管理员可使用 `cage explain`，不会执行目标命令。完整参数与权限见[诊断指南](diagnostics.md)。

## 按现象定位

| 现象 | 先查什么 | 常见原因 |
| --- | --- | --- |
| dev 启不动 | `.env` 是否在项目根目录，数据库服务是否可连接 | 缺连接、密码/端口错误、没执行迁移、端口占用 |
| init 提示账号已存在 | CAGE-INIT-002；找已有 APP/READ/MIGRATE 连接 | 角色在 PG 集群内共享；不应覆盖原密码 |
| 新业务不出现在接口/图谱 | 顶层 export const 和 domain/index.ts | 漏导出、重名导出、放进函数/条件声明 |
| API 403 | code/detail、角色能力、调用身份、硬约束 | 能力不足、CSRF、职责分离或其他业务约束不满足 |
| 详情 404 | 记录 id、租户和数据范围 | 不存在或在范围外；不能仅凭 404 断言被删除 |
| 列表为空 | read 能力、范围与相应字段 | 默认本人范围、无 owner 字段或部门不匹配 |
| 电话看不到明文 | sensitive 标注、unmask 能力 | 默认掩码是正常安全行为 |
| 有明文能力但读取报 CAGE-AUDIT-001 | requestId、审计库可用性与权限 | 可靠审计未成功，框架拒绝交付结果 |
| 生产服务拒绝启动 | CAGE-ENV-002/003、Cookie 密钥与 bootstrap 参数 | 关键配置不合格，或试图在日常启动时隐式初始化 |
| 任务时间线有 CAGE-WORKER-002 | API/worker 版本、注册指纹和消费者清单 | 旧进程或必要消费者缺失，不能把 done 当作已执行 |
| 提交成功但无待办 | worker、outbox/死信、审批路由 | 未投递、缺审批人、没有匹配的绑定/路由 |
| 已批准但 ERP 单号未回写 | worker、同步记录、死信、环境/fake | 密钥/白名单/响应错误，或异步还未完成 |
| 已取消但锁未释放 | 释放事件、反应、死信 | 先前消息阻塞、map 条件不匹配或遗漏释放 |
| 导入/导出一直 queued | worker 与任务详情 | 后台进程未启动或前序任务失败 |
| gen --check 失败 | CAGE-GEN-001/002 | 声明修改未生成、手改契约、迁移快照不一致 |

## CAGE-APPR-007：找不到审批人

先读所属领域模块 `approvals.ts` 的实际步骤（采购范例为 `packages/domain/src/modules/purchase/approvals.ts`），按选人器处理：

| 选人器 | 配置位置 | 常见误解 |
| --- | --- | --- |
| `approver.deptLeader('deptId')` | 单据 deptId 指向的部门，在 `/admin` 设置负责人 | 给用户经理角色不等于给部门设置负责人 |
| `approver.role('finance')` | 创建 code 为 finance 的角色，并给实际用户分配 | 选人看角色 code，不是中文显示名称 |
| `approver.user(id)` | 使用存在的用户 UUID，核对业务可用性 | 把用户名或角色名当成 UUID |

选人成功后，再检查此人所需能力、数据范围及结论命令的业务约束。示例中提单人不能审批自己；采购金额决定是否进入财务节点，不需要配置角色额度。

若事件已进入死信，在 `/admin` 查看对应 outboxId 的错误并修正配置，再点击重放。原 submit 通常已提交，单据处于 pending_approval；不要重复提交，更不要直接 SQL 改回 draft。重放后确认待办及后续事件，不把“点击重放成功”当成整条链路已经完成。

## CAGE-PAIR-002：新增操作遗漏释放

查看报错命令是否离开持有资源的状态，沿 `命令 → emits 事件 → reaction → releases 资源` 检查。补业务事件与真正的释放命令，声明相同资源标签，并确认 map 在这条路径能执行。

不要只加一个不执行的反应骗过图规则，也不要删 acquires 标签。图规则检查结构，业务测试还要覆盖关键条件分支。

## 数据库错误应提供什么信息

提供发生于 init/migrate/API/worker 哪一步、主机/端口/库名、使用哪个角色、PostgreSQL 错误码、是否有待执行迁移。URL 中密码特殊字符需编码；修改环境变量后重启进程。

- 连接拒绝：检查数据库服务、主机端口和容器端口映射。
- 认证失败（如 28P01）：核对对应角色密码；不重置其他项目共享角色。
- 无权限：核对当前账号职责；读账号不能用来执行迁移，业务进程不应改成管理员连接。
- 表/视图不存在：审查后执行 migrate，确认连接的是同一个数据库。
- 已执行迁移校验和不符：恢复原文件，新增迁移；不要改 sys.schema_migrations 的 checksum。

不要贴出整个 `.env`、初始化凭证文件、Cookie 密钥或恢复文件内容。管理员连接只用于准备权限，日常业务继续使用独立账号。

## 如何说明没有验证的部分

报告构建/检查通过的命令，另列跳过和未执行的检查及原因。fake 成功、图规则通过、HTTP 202、无权限用户看不到按钮，都不能单独证明真实第三方、任务完成或后端权限正确。

错误码册中的例子用于解释局部规则；完整业务代码以当前项目 domain 和生成 contracts 为准。错误来自内部源码时，手册给出路径和位置；独立项目无需把内部源码复制进来修补，应先修自己的声明/配置或明确报告框架缺口。
