# 一份声明怎样成为业务功能

以一条部门便笺为例：用户输入标题，点击创建，刷新后还能看到记录，同部门用户按授权读取，归档后不能继续编辑。Cage 把这件事分成业务声明、统一执行和页面交互三部分。

## 声明对象与允许的变化

**聚合**定义业务对象的字段、状态、归属和不变量。便笺的标题、创建人、部门与生命周期放在一起，是因为它们共同决定这条便笺是否有效。聚合通常有一张主表，也有自己的规则和操作边界。

**命令**表示一次业务意图。create 从 new 进入 active，archive 从 active 进入 archived；只修改标题的 update 使用 to: null 保持状态。声明里写允许的 from，handler 计算字段变化，内核设置最终状态。

**事件**记录已成功发生的事实。创建是否需要通知、归档是否需要释放资源，由业务决定，再用 reaction、approval 或 connector 连接后续动作。普通对象读写可以只使用聚合和命令。

这些声明是模块顶层的 export const，并沿模块入口导出到 domain 根入口。声明函数返回规格，不在导入时连接数据库或执行命令。

例如[便笺完整文件](../examples/note/note.ts)中的归档命令如下，Note 和 command 都来自该文件已声明或导入的符号：

<!-- cage:example archive-note -->
```ts
export const archiveNote = command(Note, {
  name: 'archive',
  description: '归档便笺',
  from: 'active',
  to: 'archived',
  handler: (draft) => draft,
});
```

handler 保留业务字段，状态由 to 指定并由内核写入。前端生成 note.archive(id, version)，再次归档或编辑已归档记录会在状态检查阶段拒绝，不需要在页面自己改 status。

## 注册、生成与运行各负责什么

```text
domain 导出
  └─ 注册表：识别声明、命令名称和引用关系
       ├─ API：能力目录、HTTP 路由、OpenAPI
       ├─ worker：事件消费者、审批、连接器、定时任务
       └─ CLI：本体图、前端契约、结构说明、迁移草稿
```

写了文件但没有导出，后续各层就无法使用它。check 检查声明结构，gen 生成本地文件，migrate 更新数据库，API/worker 启动时加载实际注册表。这几个步骤分别产生证据。

前端从 contracts 取得对象方法和 hooks，使用 client 处理网络、会话与结果。浏览器依赖契约和协议；领域 handler、数据库连接和运行时留在服务端。

## 一次写入怎样提交

页面通过契约发出命令请求后：

1. HTTP 处理登录会话、CSRF 和输入传输，内核校验主体、schema、调用身份与能力。
2. 内核处理请求幂等。已有对象按范围加载并加锁，再检查状态和可选的 expectedVersion。
3. 硬约束检查本次操作，例如提单人不能审批自己的申请。
4. handler 收到业务草稿、已解析输入、显式 reads 依赖，以及固定的 now 和 actorUserId，返回字段变化或业务拒绝。
5. 内核合并结果，维护创建人、状态和版本，检查字段、不变量、关联与文件绑定。
6. 业务记录、成功审计、outbox 和同事务反应一起提交；任何一步失败都会回滚这笔事务。

handler 可以等待声明的只读依赖，不能自己提交 SQL、网络或文件副作用。reads 的内部快照用于服务端计算；公开页面读取还需要经过安全读侧。

版本冲突与幂等解决不同问题：版本防止旧页面覆盖新记录；同次请求复用幂等键可以恢复已提交结果。独立的两次客户端调用默认有不同键。

## 读取怎样限制范围

普通 list/get、关联分页和 query 通过只读账号读取 safe 视图。数据库会话携带当前主体的范围与敏感字段权限；hidden 字段不作为普通公开字段，sensitive 字段按权限掩码。

归属声明告诉框架使用哪个部门或所有者字段；角色授权决定当前用户能看本人、本部门、下级部门或其他范围。按钮的 can() 只影响呈现，服务端每次操作仍要判断权限。完整规则见[权限与范围](../reference/authorization.md)。

## 同事务与异步的选择

批准申请时必须同时登记资源占用，就用 tx: 'same' 的反应调用资源命令。主命令或任一反应失败，整条事务回滚。

允许稍后完成的动作使用默认 outbox 反应。主命令先提交，worker 再消费事件；失败可能重试或进入死信。同一聚合的后续消息可能受前一条死信阻塞，因此业务页面需要区分“提交成功”和“后续完成”。

第三方请求放到连接器。数据库无法回滚已经发生的远端写入，必须依据远端协议设计幂等、结果核对与补偿。acquires/releases 只是静态资源配对标签，真正取得与释放资源仍由命令完成。具体做法见[自动化指南](../guides/automation.md)。

## 审批和 AI 怎样进入这条链

审批决定哪个节点、哪些人负责处理；结论通过 process 命令落实。被选中不会获得额外权限，最终决定人仍需符合领域授权与约束。

原生 AI 使用 ai() 启用持久运行时。助理从注册表发现授权工具，AI 审批使用现有 step 的 kind: 'ai'。模型负责提出工具计划或审核判断，服务端执行层负责授权、状态、版本、确认与回执。应用提供审核政策和界面，见[原生 AI](../guides/intelligence.md)。

## 数据库与进程的分工

| 组件 | 职责 |
| --- | --- |
| APP 账号 | API/worker 的业务事务与系统运行 |
| READ 账号 | 安全视图查询 |
| MIGRATE 账号 | 显式结构迁移与安全层更新 |
| API | 会话、协议、命令与读取入口 |
| worker | outbox、审批启动/取消、连接器、任务和运行时步进 |

框架管理连接池和事务，应用提供已有数据库的连接。首次 init 准备账号，migrate 更新结构，bootstrap 初始化组织，dev 启动进程。接管历史表需要另外设计映射与迁移。
