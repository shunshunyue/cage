## 业务声明是一份可执行规格

Cage 把业务字段、状态、写操作、读依赖和跨对象关系写成 TypeScript 声明。声明函数返回描述对象，本身不连接数据库；API 和 worker 启动时从 domain 入口构建注册表，CLI 则结合 TypeScript 源码位置抽取本体图。

同一份声明产生以下结果：

```text
domain/index.ts 导出的声明
  ├─ 注册表 → 能力目录 → HTTP 路由 → 内核与读侧
  ├─ 本体图 → 图规则 / 中文图谱 / 影响分析 / 派生测试
  └─ 生成器 → 前端 contracts / 状态图 / SQL / 迁移草稿
```

因此新增业务操作应先写领域命令，不再为该操作手写路由、权限拦截器、审计 SQL 和前端请求封装。新增声明还必须从 domain 入口导出；仅创建文件不会被自动注册。

## 聚合、命令、事件分别是什么

用“采购单”举例：

| 概念 | 例子 | 它负责的事 |
| --- | --- | --- |
| 聚合 aggregate | `PurchaseOrder` | 把金额、明细、部门、状态和不变量放在同一业务边界内 |
| 命令 command | `PurchaseOrder.submit` | 请求把草稿提交审批；执行时可拒绝，不是直接改字段 |
| 事件 event | `OrderSubmitted` | 表示提交已经成功发生，供审批等后续处理消费 |
| 反应 reaction | `lockOnApprove` | 收到已批准事件后调用库存锁命令 |
| 约束 constraint | `sod.notSameAs('createdBy')` | 执行前判断当前主体是否能进行这个业务动作 |
| 不变量 invariant | 金额必须大于零 | 执行后的对象在任何允许状态下都必须满足的条件 |

聚合通常对应 `core.purchase_order` 一张业务主表。系统列包括 `id / version / status / createdAt / updatedAt`，数据库还维护租户列；业务不要重复定义它们。`createdBy` 是业务字段，声明为 `ref('User')` 后内核会在新建时填入当前用户，并可作为本人范围与职责分离依据。

一个采购单可以有明细列表，也可以引用库存等其他聚合。跨聚合写入要调用对方的命令，通过反应表达关系，不能拿到对方数据库表直接更新。

对象关联统一写在 fields：ref 为本表外键，hasMany 依据目标外键反查，manyToMany 自动生成中间表。多对多链接属于来源对象的命令事务，但不授权修改目标内容；公开关联通过两侧安全视图分页读取。完整模式见[对象关系](../guides/relations.md)。

## 一次写入的完整路径

```text
浏览器 contracts → HTTP 会话与 CSRF → Kernel.execute
  → 校验输入、上下文、调用身份与能力
  → 幂等检查
  → 按范围加载并锁定记录，检查状态与版本
  → 硬约束（职责分离、额度、二次认证等）
  → 绑定 reads，只运行 handler 的业务计算
  → 合并结果，内核设置目标状态，校验字段及不变量
  → 写记录、版本、审计和 outbox，执行同事务反应
  → 提交事务 → 返回结果
worker → 消费 outbox → 异步反应 / 审批 / 连接器
```

- `handler(draft, input, deps, ctx)` 描述变化，可读显式声明的依赖，不直接写数据库、发 HTTP 或读写文件。
- 业务拒绝返回 `fail('业务码', detail?)`。不要抛普通异常来表示可预期的业务拒绝，也不要吞异常后返回成功。
- `from/to` 决定生命周期。handler 不能靠写 `status` 绕过状态机；已有记录的 `to: null` 明确保留当前状态，新建必须给真实目标状态。
- 乐观版本冲突用 `CONFLICT` 告知客户端重新加载；幂等用于重复投递同一个请求，二者解决不同问题。
- SDK 每次调用默认产生新的幂等键，同一次调用内部重试复用。业务要让双击或用户手动重试视为同一次提交时，需要保留并复用该次操作的键，不能假设两次独立调用自动合并。

## 同事务与异步的选择

| 声明 | 适合用途 | 失败影响 |
| --- | --- | --- |
| `reaction(..., { tx: 'same' })` | 主动作与资源登记必须同时成功，例如批准与建库存锁 | 反应失败，主命令和审计/outbox 一起回滚 |
| 默认 `tx: 'outbox'` | 可稍后完成的后续动作，例如取消后的释放 | 主动作已提交；worker 重试，耗尽或永久错误进入死信 |
| `outbound(...)` | ERP 等事务外的网络写入 | 无法回滚远端；必须设计幂等与补偿 |

同事务链不能无限递归，外部 IO 不能放进同事务 handler。异步消息按聚合顺序投递；某条进入死信后，后续同一聚合消息可能被阻塞。先修正原因，再通过死信接口重放或经业务判断丢弃，不直接修改 outbox/业务表。

资源标签 `acquires: 'inventory.lock'`、`releases: 'inventory.lock'` 为图规则提供证据。它们不会自动加锁或释放，真正效果来自 `acquireLock/releaseLock` 命令。

有界批量步骤可用 `reactionEach`：声明目标命令、最大项数、唯一排序键和映射，按稳定顺序串行调用。`order` 表达同一事件的步骤依赖，同事务链仍整体回滚。具体声明见[原语指南](../reference/primitives.md#有界集合与步骤顺序)。

出站分成外部执行与短事务回写两个阶段。框架先领取本地执行租约，用 `${tenantId}:${declaredKey}` 作为远端幂等键，可靠保存回执后再在短事务调用成功命令；回写失败可复用已保存回执。远端必须实际支持幂等，框架不能承诺任意外部系统恰好一次。不可安全重试的写入结果未知时隔离并要求核对，不能把超时当作远端未执行。

当前没有通用的远端回执确认或解除 `unknown` 的管理入口，普通死信重放不会解除未知状态。此类操作要按连接器实际协议制定受控恢复或业务补偿；不能发明恢复 API，也不能直接 SQL 改执行状态后重发。

首阶段按单机、API 与 worker 同版本升级部署。worker 启动校验必要引擎，发布消费者清单、注册指纹和心跳；不认识事件或缺少必要消费者时不会静默完成。停止时先停新任务、取消可取消 IO，再有界等待在途工作；定时任务同时使用本地运行标记与数据库互斥锁防止跨周期/实例重叠。连接器限流和认证队列均为单进程预算，多实例共享限流另需设计。

## 权限是几层判断

| 层 | 例子 | 说明 |
| --- | --- | --- |
| 登录与租户 | 当前用户与租户上下文 | Cookie 会话、OIDC 等由 HTTP 层装配 |
| 调用身份 | `user/process/job/external` | `process` 命令不给浏览器生成直接写接口；这不是角色名 |
| 能力点 | `PurchaseOrder.submit`、`PurchaseOrder.read` | 代码声明能力目录，管理员在目录范围内授权 |
| 数据范围 | 本人、本部门、部门及下级、指定部门、全部 | 决定能触及哪些记录，越范围详情通常表现为 404 |
| 业务硬约束 | 不是提单人、额度不超过 ceiling | 即使被选为审批人也必须通过 |
| 明文能力 | `PurchaseOrder.unmask.phone` | 没有该能力时，安全读侧对电话掩码 |

`scope.deptSubtree('deptId')` 描述聚合的部门字段和建议范围；**实际范围取决于角色授权数据**。`scope.none()` 表示没有部门/创建人范围字段，仍然需要能力和适当的 `all` 范围授权，不能理解成“任何人能读”。多角色范围合并为并集，缺少显式范围时默认本人范围，不是全部。

`useCan()`、`can()` 只决定按钮呈现；前端隐藏按钮不能代替后端授权。新增命令不会自动授给已有生产角色，角色分配和额度调整也受防提权约束。

授权通知监听异常时不再复用缓存，每次重新读取授权；重新订阅后清空缓存，并阻止旧请求回填旧上下文。`/readyz` 反映数据库和授权监听健康，`/healthz` 仅表示存活。诊断入口受 `Sys.ops.read` 及相关对象 read/范围控制，`explain` 解释调用身份、能力、范围、状态与硬约束，不能预测 handler 的业务结果；新建对象的最终范围无法提前确定时返回 unknown。

## 审计保证

| 入口 | 保证与失败行为 |
| --- | --- |
| 命令成功 | 与业务变更、版本和 outbox 同事务提交；写审计失败整笔回滚 |
| 命令拒绝 | FORBIDDEN / NOT_FOUND / CONSTRAINT_VIOLATED 异步尽力记录；失败有日志，不宣称所有错误均已留痕 |
| 密码登录失败 | 等待尝试写审计；失败有日志，请求仍拒绝登录，属于尽力记录 |
| get / list / related 的潜在敏感明文 | 具备相应 unmask 能力时先完成可靠审计再交付；失败拒绝结果 |
| 自定义 query | 按 reads 保守审计潜在敏感明文；声明 audit.purpose 时另外可靠记录目的；任一可靠审计失败均拒绝交付 |
| 导出生成、下载 | 可靠审计；下载还复核当前权限与访问指纹；失败不交付文件 |
| 导入任务及成功行 | 任务提交与目标命令按各自事务审计；异步逐行/原子方式见任务协议 |
| 普通掩码读取、诊断元数据 | 默认无统一专门审计 |

成功登录、step-up 和退出目前没有统一专门审计。审计保证按入口区分，不能把“有审计”理解为每一种请求都可靠留痕。可靠读取失败使用 `CAGE-AUDIT-001`，凭 requestId 定位数据库与权限故障；默认日志只保留允许的执行元数据，错误文本、原始 payload 与外部响应不进入默认结构化日志。

## 数据库连接属于框架核心能力

项目提供连接配置，框架管理连接池、事务、上下文变量和 SQL。普通业务不需要自己编写 `pg.Pool`、表仓储或连接释放逻辑。

| 配置/对象 | 职责 | 何时使用 |
| --- | --- | --- |
| `CAGE_ADMIN_DATABASE_URL` | 已有数据库的管理员连接 | 首次 `cage init` 准备账号；成功后从本地配置移除 |
| `CAGE_APP_DATABASE_URL` / `cage_app` | API 与 worker 业务写入、系统处理 | 日常运行 |
| `CAGE_READ_DATABASE_URL` / `cage_read` | 只能查询安全层 | 列表、详情、自定义查询、导出 |
| `CAGE_MIGRATE_DATABASE_URL` / `cage_migrate` | 结构变更及安全层重建 | 显式 `cage migrate` |
| `cage_view_owner` | 不可登录的视图所有者 | 安全视图内部使用，无密码配置 |

APP、READ、MIGRATE 指向**同一个已经存在的数据库**，用不同账号隔离能力。PostgreSQL 角色属于集群，不能因另一个项目初始化而重置已有角色密码。

| 命令 | 改什么 | 不负责什么 |
| --- | --- | --- |
| `init` | 角色、schema、授权、随机凭证及 `.env` | 安装 PG、启动 Docker、创建数据库、创建业务表 |
| `gen` | 本地 contracts、SQL、状态图、迁移草稿 | 应用数据库迁移 |
| `migrate` | 已有库的表、索引、安全视图、迁移历史 | 每次启动新建数据库 |
| `bootstrap` | 显式初始化组织，将初始凭据交付到新的受限文件 | 自动授予业务能力、日常启动时重置密码 |
| `dev` | 连接已有库，启动 API、worker、Web，监听声明重新生成 | 自动迁移或内嵌临时数据库兜底 |

读路径使用 `safe.*`，业务表位于 `core.*`，组织和运行数据位于 `sys.*`。安全视图结合会话上下文执行范围过滤与掩码；手写报表也必须走这层。连接现有库不意味着自动把历史任意表变成 Cage 聚合，需要专门的映射与迁移方案。

## 包之间如何依赖

业务 domain 依赖 kernel 的声明 API，按需要引用 approval/connectors 声明；API 与 worker 入口依赖 domain 并装配框架。contracts 由 domain 生成，Web 依赖 contracts 和 client。domain 不能反过来依赖 contracts，否则产生生成循环。

框架的 `testkit` 提供真实 PostgreSQL 测试环境与 handler 测试工具；`lint` 检查依赖和危险写法；CLI 负责分析、生成和汇总门禁。生产程序不需要携带整个框架仓库。

## 本体图为什么有这些连线

图谱抽取命令状态迁移与事件、反应调用、审批 start/cancelOn、约束/路由字段、查询读依赖和外部映射；另以虚线标记按标识推导的所属聚合。关系解释区分显式声明、规则推导与文本匹配，箭头要按各自含义阅读。开发前可用[本体上下文工具](../tools/ontology-context.md)检索相关业务与源码。

`cage analyze` 将图写到 `.cage/ontology.json`；`cage graph` 提供浏览器工作台。中文显示名写在 `cage.config.json` 的 `graph.labels`，例如 `"command:PurchaseOrder.submit": "提交审批"`。显示名不更改能力标识、源码符号或表名。

图规则能检查“离开持有状态是否声明了释放”等结构问题，无法证明 `map` 的任意分支或 handler 计算一定正确。因此重要的资源释放条件、权限拒绝、额度边界仍需对应业务回归用例。
