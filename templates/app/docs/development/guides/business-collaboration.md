# 与用户共同确定业务规则

需求材料描述目标，现有代码描述当前行为，框架 API 描述可用机制。三者含义不同。开发者需要把它们连接成可执行、可验收的规则。

## 先找会影响结果的问题

阅读用户描述、项目约定与受影响模块，确定：

- 对象代表什么，哪些信息是事实，哪些只是显示名称或历史快照。
- 谁可以做什么，记录属于本人、部门还是其他组织范围。
- 操作前后处于什么状态，撤回、失败、重复提交如何处理。
- 金额、数量和时间的单位、精度、边界值。
- 页面需要显示什么，怎样观察保存或流程已完成。

只处理与本次目标相关的问题。用户已明确的条件直接沿用；发现材料互相冲突时引用具体位置。代码正在执行某条规则，并不能单独证明它就是用户希望保留的规则。

例如用户说“归档后保留历史”，先确认归档后是否还能修改、是否可恢复、谁能恢复；若本次只改按钮文字，就直接修改文案，不把这些无关业务问题重新问一遍。

## 区分业务决定与技术查证

| 情况 | 下一步 |
| --- | --- |
| “大额增加审核”没有阈值，或不含等于边界 | 解释影响，给出可行规则和推荐，让用户选择 |
| 两份制度的可见范围不同 | 指出冲突和现有行为，确认应采用的业务口径 |
| 文档写的 API 与当前包不符 | 查真实导出、签名及实现，报告查证结果 |
| 目标超出框架能力 | 说明具体缺口，比较可行方案、成本及行为差异 |
| 命名、文件归属、一般组件组织 | 按项目规范自行处理 |
| 有价值的可选改进 | 说明收益和额外范围，继续已明确工作 |

业务规则需要选择时再提问。技术事实由开发者查清；已明确方案也不额外设置批准步骤。

例如“框架有没有多对多”由开发者查公开导出和关系实现；“成员是否能看到全部便笺”由用户决定。前者不应反问用户选 API，后者也不能因为框架默认本人范围就擅自替用户决定。

## 一个问题要帮助用户判断

说明疑点来自哪里，为什么会改变结果；给出少量可行选项，解释用户能观察到的区别，再给出推荐和依据。用业务语言提问，例如“提交后谁还能修改”，实现时再决定对应的命令和状态。

优先问影响下一步的问题，相关问题合并。用户只回答部分时，保留答案并继续处理剩余疑点；推荐选项、界面预选、等待时间或沉默不算用户选择。等待时可以查证或实现不依赖该决定的部分。

例如用户已经确认“归档后不可编辑”，但尚未回答谁能恢复：可以实现归档和禁止编辑，恢复命令保持待定；不能因为推荐了“创建人恢复”就直接做成生产规则。

例如制度写“低于 5000 元由部门负责人审批，超过 5000 元增加财务”。恰好 5000 元没有覆盖，需要选择“大于等于”还是“严格大于”。确认后分别用 4999.99、5000、5000.01 验证；如果顺序还是并行仍不明确，另行处理这个问题。

## 把答案变成后续能使用的规则

保留选择本身的含义与来源，例如“满 5000 元增加财务”，而不只记“同意方案 A”。记录已确定事项、待定事项和可选建议；简单修改在对话中说明即可，长期业务约定放项目文档或 AGENTS 托管区外。

用户改变规则时，更新受影响的声明、页面、数据处理和验收。授权与已给出的答案继续有效；发现实现缺口时带证据和替代方案回来说明。
