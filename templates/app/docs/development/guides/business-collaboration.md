# 业务澄清与共同设计

[返回学习入口](../README.md) · [框架开发 Skill](../skills/cage-development/SKILL.md) · [业务设计与能力选择](recipes.md)

用户可能只有一个目标，业务文档也可能有遗漏、歧义或相互冲突的规则。agent 阅读后应主动提出疑问和建议，帮助用户比较方案、作出选择，再把选择落实为 Cage 业务声明与验收结果。本页用于开发时的协作，不是应用内 AI 助理的交互协议。

## 先核对事实，找出需要共同决定的事

先读当前对话、项目业务约定和受影响的源码，区分“用户希望怎样”“文档约定怎样”“系统现在怎样”。已经明确的需求沿用；用户明确要求改变旧规则时说明影响并执行，不因为旧文档不同而重复请求同一决定。

主动检查对象和术语、参与人及范围、状态与动作、金额/数量/时间口径、失败与撤回、页面体验和验收标准。只检查本次相关内容，不要求用户先填写一份完整问卷。发现疑点应尽量说明具体位置和影响，不把未说明的内容当作默认允许，也不照搬采购示例中的规则。

| 发现的情况 | agent 如何处理 | 用户需要决定什么 |
| --- | --- | --- |
| “大额需审批”“负责人可见”等描述有多种解释 | 指出缺失的阈值、负责人来源或可见范围，列出可行理解及影响 | 业务口径与希望的行为 |
| 业务文档互相矛盾，或与现有行为不一致 | 引用冲突位置，说明当前实现；已有明确新要求时直接采用，否则给出调整方案 | 哪条规则应作为目标，变更适用范围 |
| 框架文档写法不清、签名或版本不一致 | 按[能力诊断](../tools/diagnostics.md)核对安装版本、公开导出与实现，说明查证结果和仍不确定的部分 | 仅在影响业务目标或实现范围时选择方案；API 是否存在由证据确定 |
| 需求无法由当前能力直接表达 | 说明缺口，比较已有能力可实现的方案、应用扩展或框架扩展及成本；只提供有依据的选项 | 保留目标并扩展、接受明确的行为调整，或延后相关部分 |
| 规则可实现，但存在更清楚的使用方式或遗漏的失败体验 | 提出具体建议，解释收益和额外工作，标明是可选改进 | 是否纳入本次；未采纳不妨碍已明确工作 |
| 命名、目录归属、普通组件组织等技术选择 | 按项目约定和框架指南自行解决；有实质业务影响时再说明 | 通常无需选择实现细节 |

代码能说明当前行为，框架文档能说明能力边界，都不能单独证明用户希望的业务。查证不能解决的业务疑问要提出；已经查明的技术事实不转交用户猜测。资料确有错误时指出来源，在任务授权范围内修正或记录，不把猜测写成已实现能力。

## 每次提问都帮助用户作选择

一个有用的问题通常包含以下内容，按复杂程度合并表达即可：

1. **疑点与依据**：哪句话、哪段规则或哪个现有行为有问题，以及为什么会影响结果。
2. **选项与影响**：给出少量可行方案，通常两到三个；说明用户能观察到的区别，以及必要的配置、实现成本或框架限制。允许用户补充其他方案。
3. **推荐与理由**：结合已知业务、现有实现和框架能力推荐一个方案。缺乏推荐依据时说明还缺什么事实，不为了给建议而编造行业规则。
4. **本次需要的决定**：明确让用户选择哪个业务规则，以及未决定前哪一部分暂不落实。

例如应问“提交后哪些人可以修改申请”，再由 agent 选择对应命令和状态约束；不要让用户先决定 `from/to` 怎样写。金额阈值、审批人、数据可见范围等也不能从示例或技术便利性推断。

优先提出影响下一步设计的少量问题，相关问题可以合并。其余已发现疑点简短列为后续事项，随工作推进继续澄清；不要为了减少提问而隐去重要疑点，也不要一次倾倒所有可能的问题。用户只回答一部分时，保留这些答案，下一轮只追问剩余的相关事项。

## 在选择中推进实现

- 对需要业务选择的部分，在获得答案前保留为待定；可以继续阅读、核对能力、实现不依赖该决定的部分。不要把待定策略写成生效的权限、金额计算或状态规则。
- 可选改进单独说明；已明确任务照常推进。不要把每个建议都变成一个必须批准的关卡。
- 用户已有明确选择、授权或要求“你来定”时，按该范围推进并说明采用的规则。推荐选项、界面预选、等待时间和沉默均不构成新的选择；用户委托决定也不扩大任务或外部操作的授权范围。
- 实现中发现约定无法落地时，带着实际证据和替代方案回到用户，不默默降低要求。用户改变规则时，先指出受影响的声明、页面、数据和验收，再修改相关部分，无需重新确认无关规则。

简单任务在对话中简短记录即可；需要后续维护的规则写入项目已有业务文档或 AGENTS.md 的托管区外，并从项目入口引用。保留“已确定的规则及依据”“尚待决定的事项”“可选建议”的区别。客户业务事实不写进框架通用教材，也不写进会被 `cage sync` 覆盖的区域。

回答应变成可以核对的业务规则和验收例子，保留来源；不要只记“用户同意方案 A”，丢失选项当时的含义。接着查证现有实现与框架能力，按[编码前的实现映射](recipes.md#写代码前的实现映射)说明如何落到声明、页面、配置和验收，再实施。只有规则已确定而技术做法尚未查清时，继续查证，不把技术猜测混进用户的业务选择。

记录不要求固定文件格式，也不要求每项小改动新增计划文件。已明确的技术方案无需再设一轮批准，普通实现取舍由 agent 负责。

## 示例：文档没有写清金额边界

业务文档写着：“金额低于 5000 元由部门负责人审批；超过 5000 元增加财务审批。”

agent 读后可以提出：

> 这两条规则没有覆盖恰好 5000 元，会影响审批路径。可以选择：
>
> - A：满 5000 元就增加财务审批。
> - B：5000 元仍只由部门负责人审批，超过才增加财务。
>
> 我建议 A，让阈值本身也经过财务审核；这是一项待你选择的业务规则。你希望采用哪一种？也可以指定其他边界。

用户选择 A 后，agent 将规则落实为“低于 5000 元仅部门负责人审批；大于等于 5000 元增加财务”，按当前审批能力实现条件，并验证 4999.99、5000、5000.01 元三种输入。金额精度和单位仍沿用项目约定；若尚未约定且影响实现，也应继续提出。

如果文档还没说明财务与部门负责人的先后关系，这仍是独立疑点：说明顺序审批和并行审批的业务区别及当前支持方式，再让用户选择。金额边界已有答案，不再重复询问；选人、授权和真实待办的验收按[审批指南](approvals.md)落实。
