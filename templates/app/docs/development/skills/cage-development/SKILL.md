# 使用 Cage 开发业务

本 Skill 是编程 agent 的工作流程：**读项目 → 理解需求并澄清 → 查证框架与现有实现 → 说明实现映射 → 编码 → 按业务验收**。先知道用户要什么、Cage 如何实现，再改代码；不要从一句需求直接套用熟悉的技术方案。

按当前任务使用本流程，保留项目自己的业务规则和用户授权边界。案例中的对象、角色和流程不代表当前应用的需求。这里指导开发阶段的 agent；应用内原生 AI 的接入另见[智能化指南](../../guides/intelligence.md)。

## 先建立正确的运行模型

Cage 是由业务声明驱动的框架。应用定义业务含义，框架执行这些声明。

```text
定义阶段：领域声明 → domain 导出 → 注册表
                              ├─ 能力、HTTP 接口与运行时
                              └─ 本体图、前端契约与迁移草稿
写入阶段：页面 → 生成契约 → HTTP → 内核执行命令 → 数据、审计与事件
读取阶段：页面 → 生成的 list/get 或 query → 安全读侧 → 当前主体可见的数据
后续阶段：事件 → 同事务反应，或 outbox → worker → 反应 / 审批 / 连接器
```

- **聚合**定义一个业务对象的字段、状态、归属和不变量。以生命周期和一致性要求划分边界；关联对象可以有自己的生命周期。
- **命令**表达业务意图，是业务写入口。`from/to` 声明允许的状态变化，handler 根据草稿、输入与 `reads` 依赖返回变化；内核处理授权、范围、版本、事务、审计与 outbox。handler 不执行数据库、网络或文件 IO。
- **读取**使用生成的读取接口；复杂汇总声明 query，通过 `safe.*` 查询。页面展示的数据来自这些服务端结果。
- **事件**表达已发生的事实；reaction 调用后续命令。共同成功的变化用 `tx: 'same'`，允许稍后完成的变化使用异步执行，并处理失败和重试。
- **权限**分别考虑角色分配、能力点、数据范围、调用身份和业务约束。`user/process/job/external` 是调用身份；`can()` 是界面提示。角色名称、页面门户和审批选人均不能代替授权。
- **页面**管理表单、弹窗与展示，并通过契约执行业务。声明存在、接口生成、应用启用和实际执行成功是四种不同证据。

首次接触 Cage，先读[架构与执行模型](../../getting-started/architecture.md)，再沿[第一条完整业务链](../../getting-started/first-feature.md)理解声明如何变成真实读写。已经熟悉框架时只读当前缺失的部分；不要把教学案例整体加入用户项目。

## 1. 确认正在修改什么

读取当前项目的 AGENTS.md、package.json、cage.config.json，以及相关模块的入口和现有测试。确认：

- 当前工作目录是框架源码仓库，还是依赖框架的应用。框架仓库的业务范例在 `examples/purchase-admin`；普通应用命令在对应应用根目录执行。
- 当前安装版本、domain 入口、契约目录和真实前端入口。API 以该版本的公开导出与生成契约为准。
- 任务属于新建业务、扩展已有业务、排错，还是界面调整。界面文案或样式调整不重新建模；排错先定位现有链路，避免重写一套实现。
- 参考代码和正在运行的代码分别在哪里。空白项目的 `docs/examples/purchase-admin` 只供阅读。

先复用已存在的声明、客户端与组织基础。区分用户希望实现的规则、文档中的约定与代码当前的行为；现有代码只能证明现在怎样运行，不能替用户决定目标业务。用户已明确的条件直接采用，发现仍未解决的歧义、冲突或遗漏时按下一节共同澄清。

## 2. 提出疑问和建议，与用户共同确定业务

先用业务语言整理本次目标：谁要完成什么事，操作前后发生什么变化，哪些条件必须成立，怎样才算完成。区分用户明确提出的规则、文档和代码提供的事实、尚待决定的问题及可选建议；只整理本次相关内容，不能用一份功能名列表代替业务理解。

按[业务澄清与共同设计](../../guides/business-collaboration.md)处理不完整的描述和不清楚的文档。主动指出可能影响业务含义、使用体验、实现范围或验收的疑点，不等到实现失败才询问，也不默默补成自定规则。

- 先读相关上下文；API、版本与当前行为由 agent 查文档、公开签名和实现证据。查证后仍涉及业务取舍的，交给用户选择。
- 提问带上具体疑点及来源、可行选项与影响、推荐方案及理由。用用户能判断的业务语言表达，允许用户提出选项之外的方案；框架缺口和额外实现成本要说明。
- 按对当前工作的影响分批提出问题，也可提出有价值的改进建议。需要选择的业务规则先取得答案再实现相关部分；等待时推进独立工作。可选建议不阻塞已明确的任务。
- 沿用用户已给出的选择和授权，不重复确认。普通技术细节自行解决；用户明确委托 agent 决定时，在委托范围内选择并说明依据。推荐、预选和未回复均不等于用户已选择。
- 将回答更新为业务规则和验收例子，再映射到框架；实现中发现新疑问仍按此方式处理，用户改主意时同步调整受影响的部分。

## 3. 选择已有能力并核对用法

带着已理解的业务动作，按[业务设计与能力选择](../../guides/recipes.md)判断聚合、一致性和能力边界，再按下表查用法。先看当前应用有没有对应实现，再决定复用、修改还是新增；不要先设计一套通用后端，再尝试套进 Cage。先看最小接入，再查高级选项，不要一次加载所有专题。

| 需求 | 选择方法与学习入口 |
| --- | --- |
| 新对象、状态、业务操作 | [原语](../../reference/primitives.md)：先确定命令意图；已有记录只改字段使用 `to: null`，仍检查允许状态 |
| 对象/状态看不懂、关系和联动不清楚 | [本体建模](../../guides/ontology-modeling.md)：业务含义落实到真实声明，名称完整性与业务正确性分别核对 |
| 一对多、多对多 | [关系](../../guides/relations.md)：只读反查选 hasMany；纯链接选 manyToMany；关系有独立状态/属性时再建聚合 |
| 列表、详情、统计 | 普通 list/get 优先；汇总或联表使用[query](../../reference/primitives.md#两种查询写法)，显式 reads 与安全视图 |
| 角色、本人/部门范围、敏感字段 | [授权模型](../../getting-started/architecture.md#权限是几层判断)：先定归属字段，再配置能力和范围，核对当前会话公开字段 |
| 审批和人员流转 | [审批](../../guides/approvals.md)：提交事件、approval 绑定、route、结论命令；页面通过待办接口决定，选人和授权分别检查 |
| 事件联动、资源占用、定时动作 | [原语](../../reference/primitives.md)：显式 emits/reads/calls，按一致性要求选择事务边界；资源标签还需实际命令落实 |
| 上传、下载、断点续传 | [文件](../../guides/files.md)：上传字节获得文件 ID，业务命令绑定，受控接口下载 |
| 导入、导出 | [数据传输](../../guides/transfers.md)：导入逐条或原子执行命令，导出异步读取；跟踪任务到终态 |
| 第三方系统 | [连接器配方](../../guides/recipes.md#接入外部系统)：外呼、验签、幂等、回写命令与失败恢复 |
| 原生 AI、AI 审批、随页助理 | [智能化](../../guides/intelligence.md)：先检查已有框架能力和 domain 启用状态，再配置策略、授权、模型与界面 |
| 页面、导航、会话与组件 | [目录](../../reference/project-structure.md)、[路由](../../guides/routing.md)与[前端组件](../../guides/frontend-ui.md)：AI 生成真实 React 页面、Ant Design 组合、模块公开入口、独立 URL、会话恢复与用户缓存清理 |

知道任务类别时直接阅读上表的章节；需要定位具体术语时先用本地文本搜索。在应用根目录使用：

```sh
rg -n "术语或符号" docs/development docs/errors
pnpm exec cage capabilities "公开符号" --format json
pnpm exec cage context "当前业务关键词" --format json
```

三者分别回答“手册怎样教”“当前版本提供什么”“当前应用在哪里实现”。没有 rg 时使用宿主的本地文件搜索。按命中位置阅读完整规则和代码上下文；结果为空时改用目录中的术语或公开符号，不能由一次未命中推断能力缺失。教材直接保存在本地，无需向量模型、索引构建或独立服务。

调用前确认真实签名、参数、返回结果和前提。类型断言不能增加服务端实际未返回的字段。若当前版本确有缺口，说明具体缺口，给出有依据的可行方案及其业务影响，让用户选择涉及目标或范围变化的方案，同时继续处理独立部分；不要编造 API、复制框架运行时或用本地模拟补足正式业务。

## 4. 写代码前说明实现映射

对准备实现的部分，向用户简述以下对应关系；示例见[规则到实现的映射](../../guides/recipes.md#写代码前的实现映射)。这一步应发生在修改业务代码之前，不能写完后再补一份解释。

| 要说明什么 | 必须有的依据 |
| --- | --- |
| 本次要实现的业务行为 | 已明确的目标、规则和来源；尚待决定的事项单列 |
| Cage 如何实现 | 已查证的聚合、命令、状态、范围及必要的后续流程；具体指南、公开签名或现有声明位置 |
| 具体改哪里 | 复用或修改的模块与导出、需要生成的契约/迁移、页面入口及运行前提；区分框架已提供和应用需完成的部分 |
| 怎样证明完成 | 用户能观察到的成功结果，以及相关的权限、状态、边界值或失败情形 |

每个业务提交按钮应对应真实契约，每项可见范围应有服务端归属和授权依据，每个自动后续动作应有执行与失败处理路径。对应不上时先查证或补设计；涉及业务取舍则回到第 2 步，不用猜测、类型断言或模拟数据填空。

新建或修改领域时，按[本体建模](../../guides/ontology-modeling.md)说明相关对象的业务含义、关系方向/基数、状态与动作前后结果，再映射到 ref/集合关系、states、命令及必要的触发链。自然语言、文档、表格和原型都是需求证据；不能按页面建表、按字段名猜外键，或把读取箭头当自动联动。聚合/字段/命令等填写结构化描述，每个状态填写 labels；普通注释和页面文案不会自动进入图谱。

清楚的小改动用一两句话即可，不要求新建计划文件，也不要求用户批准普通技术方案。已有明确需求与授权就继续实施；只有尚未确定的业务选择阻塞依赖它的部分。需求或能力证据变化时更新这份映射，避免实现与已选规则脱节。

## 5. 沿一条真实链路实施，再扩展

新业务先完成一个动作的保存与读取；已有业务只贯通受影响的动作。按[开发步骤](../../getting-started/workflow.md)操作：

1. 涉及已有领域含义变化时先保存本体基线。按[目录规范](../../reference/project-structure.md)修改声明，从模块 index 到 domain 入口导出；handler 的读取与 job 的调用声明依赖。
2. 运行 check/gen，检查生成契约和迁移草稿。生成内容说明声明被识别；需要结构变化时审查后执行迁移，保留已发布迁移。
3. 按当前环境准备实际授权与必要配置；应用入口和 worker 加载一致的 domain。新能力不自动授给生产角色，沿用用户已授权的配置范围。
4. 页面调用实际生成的方法并处理业务失败。底层 `CageResult` 检查 `ok`；hook 的成功/失败语义以当前 API 为准。成功后重新读取或失效对应查询；失败保留输入并给出可操作提示。
5. 验证一个完整动作后复用该模式扩展。前端临时状态可保存草稿、筛选和弹窗；正式业务记录、审批结果及权限由服务端决定。测试夹具或用户明确要求的原型要标明用途，不作为正式运行结果交付。

编写时同步遵守[中文注释规范](../../reference/commenting.md)：说明职责、输入输出、调用关系和实际边界。注释中的保证必须能在代码中找到实现。

## 6. 用观察结果决定完成程度

验证与改动匹配，不因小改动运行全部数据库测试。逐项回到编码前的规则与验收例子，检查实现和生成结果是否落实了选择、是否混入未要求的业务行为；待决定事项不能报告为已完成。对新的业务读写链，至少核对所涉及的以下证据：

| 要证明什么 | 应取得的证据 |
| --- | --- |
| 声明与接口相符 | check、生成一致性、类型检查以及实际契约调用 |
| 本体可理解且符合需求 | 处理本次声明的 CAGE-ONTOLOGY-001，按业务用语检查图谱/context；逐项核对关系、状态和触发依据，再用业务例子验证，名称齐全不等于业务正确 |
| 数据持久保存 | 命令成功后通过安全接口独立读取；页面重新加载使用同一服务端记录 |
| 权限与范围生效 | 允许主体成功，范围外或缺能力主体的直接请求被拒绝 |
| 流程真正执行 | 提交、待办、决定、结论命令及最终业务状态对应起来 |
| 文件真正保存 | 上传原始内容，绑定成功，授权下载内容一致，越权下载拒绝 |
| 异步工作完成 | 实际任务终态和业务结果；接受请求或 fake 成功只证明对应阶段 |
| 页面可用 | 按[浏览器验收](../../guides/routing.md)实际操作对应路径，包含错误/无权限及相关导航行为 |

检查通过不能扩大解释为未检查的业务结果。交付分别报告通过、跳过、未执行，附具体行为与证据；缺少运行条件时明确剩余验证，不伪造成功记录。

## 7. 遇到失败，沿边界定位

先保留 `code / at / reason / fix` 和相关操作事实，查[排错方法](../../tools/troubleshooting.md)与[错误码册](../../../errors/README.md)。从页面真实调用开始，定位第一个不符合预期的边界，再做最小修正：

- 页面未发请求：查事件处理器和数据来源。
- 契约缺方法或图中缺节点：查导出、生成及当前版本。
- 请求拒绝：查认证、能力、范围、状态、版本和业务约束。
- 请求成功但后续未完成：查实际事件、worker、待办或任务执行记录。
- 服务端正确但页面陈旧：查查询失效、URL 和用户缓存。

不要通过放宽授权、删除约束、关闭门禁或改写迁移历史消除错误。找到具体实现缺口再扩展框架；框架内部修改遵守框架仓库的维护规则。
